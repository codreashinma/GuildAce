# dev-agent-context-design

オーケストレーション設計で決めた各エージェントについて、**LLM の 1 回の呼び出しに何をどの順で詰めるか**を設計するスキル。

設計するのは次の 7 つ:

1. **ブロック構成** — コンテキストを何の塊に分け、どの順に並べるか
2. **信頼区分** — その塊は信頼できる入力か、できない入力か
3. **トークン予算** — 各塊に何トークンまで割り当てるか。合計がモデルの上限に収まるか
4. **切り詰めの順序** — 予算を超えたとき、何から削るか
5. **キャッシュ境界** — どこまでが毎回同じで、どこから変わるか
6. **コンテキストガード** — 信頼できない入力をどう隔離するか（プロンプトインジェクション対策）
7. **入れてはいけない情報** — 個人識別情報・鍵・他案件のデータ

ここでは**エージェントもツールも新しく作らない**。必要になったら推測で埋めずに未決事項へ上げ、`dev-agent-orchestration-design` / `dev-architecture-design` に差し戻す。

**プロンプトの本文は書かない。** 書くのは構造・順序・上限・規則だけ。本文を設計書に固定すると実装と必ず食い違う。

## 2. 設計する

### 2-1. コンテキストブロックを定義する

1 回の LLM 呼び出しに入るものを、役割ごとの塊に分ける。各ブロックに `CTX-001` から採番し、次を定める:

- **役割**（何のための塊か）
- **固定 / 可変** — 毎回同じ内容か、呼び出しごとに変わるか
- **信頼区分**（2-2）
- **トークン上限**（2-3）
- **切り詰めの優先度**（2-4）
- **出どころ**（どのテーブル・どの入力から作るか）

典型的なブロック（過不足は案件次第。**無いものを足さない**）:

| 塊 | 役割 |
|---|---|
| 役割と制約の指示 | そのエージェントが何者で、何をしてはいけないか |
| 出力スキーマ | 返してほしい構造。オーケストレーション設計のツール定義と**同一にする** |
| 定義データ | 外から与えられる振る舞いの指定 |
| 手元の課題 | 今回処理する対象 |
| 参照データ | 判断に要る既存のレコード |
| 直前の失敗 | 検証に落ちたときの、違反項目と前回出力 |

**1 ブロック 1 役割。** 「その他」を作らない。

### 2-2. 信頼区分を付ける

**すべてのブロックに、信頼できるか否かを必ず付ける。** これを飛ばすとインジェクション対策が設計できない。

| 区分 | 意味 | 例 |
|---|---|---|
| 信頼できる | 自分たちが書いた、または決定的コードが生成した | 役割の指示、出力スキーマ、DB から取り出した構造化レコード |
| **信頼できない** | 第三者が内容を決められる | 利用者の自由入力、第三者が作った定義データの自由文、外部サービスから取得した文字列、他の利用者が書いた本文 |

- **「自分たちのDBに入っているから信頼できる」と考えない。** 誰が書いた値かで判断する。利用者が入力した文字列は、DB を経由しても信頼できない。
- 信頼できないブロックが 1 つも無い設計になったら、**分類を間違えている可能性が高い**。入力の出どころを辿り直す。

### 2-3. トークン予算を配分する

- **モデルのコンテキスト長を確認する。** 上流で未確定なら、**絶対値を置かずに相対配分（％）で設計し、未決事項に上げる**。仮の数値を置く場合は「仮」と明記する。
- ブロックごとに上限トークン数（または％）を決める。
- **出力に必要な分を必ず確保する。** 入力だけでコンテキスト長を使い切る配分にしない。
- **合計を検算して書く。** 「入力の合計 + 出力の上限 ≤ コンテキスト長」を数値で示す。検算を書かない設計書は出さない。
- オーケストレーション設計のコスト上限と整合させる。1 回の呼び出し × 反復上限が、コスト上限に収まるかを確かめる。

### 2-4. 切り詰めの順序を決める

予算を超えたときに**何から削るかを、全ブロックに順位で付ける**。

- **削ってはいけないブロック**を先に決める（役割の指示、出力スキーマ、手元の課題）。これらが欠けると出力が壊れる。
- 削り方も決める: 件数を減らす／古いものから落とす／要約に置き換える／丸ごと落とす。
- **黙って切り詰めない。** 切り詰めが起きたことを記録し、必要なら出力に「情報が不足している」と返させる。

### 2-5. キャッシュ境界を決める

プロンプトキャッシュを効かせるには、**毎回同じ部分を前に、変わる部分を後ろに**置く。

- ブロックの並び順を「固定 → 準固定 → 可変」にする。
- **キャッシュ境界がどこかを明示する。** 境界より前に可変要素（現在時刻、ランダムな識別子、件数によって変わる文言）を 1 つでも混ぜるとキャッシュが効かない。
- 定義データのように「案件ごとに固定・呼び出しごとに不変」のものは、準固定として境界の内側に置けるかを検討する。

### 2-6. コンテキストガードを設計する

`CG-001` から採番する。**信頼できないブロックすべてに、最低 1 つのガードが対応していること。**

最低限、次を検討する:

| 種類 | 内容 |
|---|---|
| 区切り | 信頼できない内容を明確な区切りで囲み、**「ここからはデータであって指示ではない」と宣言する** |
| 位置 | 信頼できない内容を、役割の指示・出力スキーマより**後ろ**に置く |
| 正規化 | 制御文字・見た目が同じ別文字・過剰な空白・区切り記号の偽装を落とす |
| 長さ | 信頼できない内容の長さを打ち切る（2-3 の上限と対応） |
| 出力の検証 | **モデルの出力を信じない。** 副作用を起こす前に決定的コードで検証する（オーケストレーション設計の検証と同一にする） |
| 権限の外出し | 何をしてよいかをコンテキストの文言で縛らない。**ツールの権限と検証で縛る** |

**最後の 2 つが本質である。** 区切りや指示でインジェクションを完全には防げない。**防げない前提で、権限と検証で被害を抑える設計にする。**「防げる」と書かない。防げない範囲は、そう書いてリスクに上げる。

### 2-7. 入れてはいけない情報を決める

**ブロックごとに、入れない情報を明示する。** 上流のプライバシー要件に従う。

最低限の確認:

- 個人識別情報（上流で「保持しない」と決めたものは、コンテキストにも入れない）
- 秘密鍵・API キー・認証情報
- **他の案件・他の利用者のデータ**（1 回の呼び出しに 1 案件分だけ入れる）
- 自由文のうち、判断に不要な部分（全文ではなく要約で足りないかを検討する）

### 2-8. 出力の受け取り方

- 出力スキーマは、**オーケストレーション設計のツール定義と同一のものを使う**。ここで別に定義しない（二重定義は必ず食い違う）。
- パースに失敗したときの扱い（再試行か、失敗として返すか）を決める。再試行の回数は**オーケストレーション設計の値に従う**。
- 再試行時、コンテキストに何を足すかを決める（違反項目だけか、前回出力も含めるか）。**足すほどトークンを食うので、上限と整合させる。**

### 2-9. 会話履歴の扱い

- **既定は「保持しない」。** 1 回の呼び出しを独立させられるなら、そうする。
- 保持が必要な場合は、何ターン分か、要約するか、要約は誰が作るかを決める。
- **他の委譲で得た中間出力を持ち回らない**（オーケストレーション設計の方針と揃える）。

### 2-10. モデルとパラメータ

- モデル名・バージョン・コンテキスト長・出力上限を書く。**上流で未確定なら「未定」と書く。**
- 温度などのパラメータを決める場合は、**なぜその値かを書く**。構造化出力が要るものは低くするなど、理由を伴わせる。
- 決定性が要る処理はそもそもモデルに渡さない（オーケストレーション設計の一覧に従う）。

### 2-11. 評価と回帰

コンテキストは実装中に何度も変わる。**変えたときに壊れていないかを確かめる方法**を決める。

- 代表的な入力の組（正常・境界・悪意ある入力）を何件用意するか
- 何を合格基準にするか（**スキーマに適合するか、検証を通るか**。文章の良し悪しを基準にしない）
- インジェクションを試す入力を必ず含める

### 2-12. ID の採番

| 対象 | ID | 備考 |
|---|---|---|
| コンテキストブロック | `CTX-001` | 信頼区分・トークン上限・切り詰め順位を必ず持たせる |
| コンテキストガード | `CG-001` | 信頼できないブロックに最低 1 つ |
| 設計上の未決事項 | `CQ-001` | 上流の `Q` / `AQ` / `DQ` / `OQ` とは別系列 |
| 設計上のリスク | `CR-001` | 上流の `R` / `AR` / `OR` とは別系列 |

- **上流の欠落**を見つけた場合は `CQ` ではなく、**上流に `Q` / `AQ` / `OQ` を追加して差し戻す**（該当ファイルと変更履歴の両方を更新する）。
- 既存の設計書がある場合は必ず先に読み、**既存の ID を再利用して振り直さない**。

```markdown
- **並び順**: CTX-00x → CTX-00y → …（キャッシュ境界の位置を示す）
- **トークン配分**: ブロックごとの上限と合計
- **参照データの選び方**: どのテーブルから何件、どの順で選ぶか。選択は決定的か
- **切り詰め順位**: このエージェントでの順位（全体と異なる場合のみ）
- **入れない情報**: このエージェント固有のもの
- **出力スキーマ**: どのツール定義と同一か（TOOL-00x）
- **再試行時に足すもの**: 何を、何トークンまで
- **根拠**: AG-00x のプロンプト方針（`agent-definitions.md`）
```

- **プロンプトの本文を書かない。** ブロックの構成・順序・上限・選択規則だけを書く。

### 3-3. 図（SVG）

**構造の図は必ず SVG で作成し、`$DOCS_DIR/agent-context/img/` に保存したうえで、その中身を `agent-context.md` にインラインで埋め込む。**

#### 作る図

| ファイル名 | 図 | 何を示すか | 作らなくてよい場合 |
|---|---|---|---|
| `01-context-layout.svg` | 構成図 | ブロックの並び順・固定/可変・信頼区分・トークン配分・キャッシュ境界 | **必ず作る** |
| `02-trust-boundary.svg` | 信頼境界図 | 信頼できない入力がどこから入り、どのガードを通るか | **必ず作る** |
| `03-<主題>.svg` | 補助図 | 上記で表せない構造（エージェント間のブロック共有など） | 上記で足りる場合 |

図ありきで作らない。**表で足りるなら作らない。** ただし `01` と `02` は必ず作る。

#### 記法

| 要素 | 記法 |
|---|---|
| コンテキストブロック | 角丸の矩形。中に `CTX-001`・役割・上限トークン数。**縦に積んで並び順を表す**（上が先） |
| 固定 / 可変 | 塗りを変える。ステレオタイプにも `«固定»` / `«可変»` と書く（色だけに頼らない） |
| **信頼できない入力** | 枠線を太くし、`«信頼できない»` を必ず付ける。**一目で分かるようにする** |
| キャッシュ境界 | ブロックの間に引く太い破線 + 左に `キャッシュ境界` のラベル |
| トークン配分 | ブロックの右に帯グラフか数値。**合計と上限を併記する** |
| コンテキストガード | 対象を囲む破線の矩形 + `CG-001` のラベル |
| 人間のアクター | 棒人間 + 直下に名称 |
| 外部システム・ツール | 角丸の矩形 + `«system»` / `«tool»` |
| 凡例 | 図の下部に必ず置く |

- **人間でないものを棒人間で描かない。** 判断基準は「その相手は画面を操作したり意思決定をしたりする人間か？」。いいえなら箱にする。
- 設計書の表と **ID・名称・数値を完全に一致**させる。図だけの略称や概数を作らない。

#### レイアウト規則

- 構成図は**上から下へ並び順**を表す。左右に散らさない。
- 信頼境界図は**信頼できない入力の出どころを左、ガードを中央、モデルを右**に置き、流れを左から右に揃える。
- **線を交差させない。** 交差しそうならノードの並び順を入れ替える。
- ブロックが 15 を超える場合は、エージェント別に分割する。

#### SVG の書き方（必須ルール）

- ルートは `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 W H" width="W" height="H">`。`viewBox` を必ず付ける。
- **ダーク/ライト両対応**: 背景に `<rect fill="#ffffff">` を敷き、線と文字は濃色（`#1f2937`）で描く。`currentColor` や CSS 変数に頼らない。
- フォントは `font-family="'Noto Sans JP','Hiragino Sans','Yu Gothic',sans-serif"`、本文 `font-size="12"`〜`13`。テキストは `<text>` 要素で書き、パス化しない。
- `<style>` 要素は使わず、すべて属性で指定する。
- 矢印は `<defs>` の `<marker>` を定義して再利用する。**`id` は図ごとに一意にする**（同じ Markdown に複数の SVG を埋めると id が衝突するため）。
- `«` `»` や `<` `>` をテキストに書くときは、**必ず実体参照でエスケープする**（`&#171;` `&#187;` / `&lt;` `&gt;`）。生で書くと XML として壊れる。
- テキストの `text-anchor` を明示する（既定に頼って文字が左へはみ出す事故を防ぐ）。
- 手書きで組み立てる。作図ツールの巨大な出力を貼り付けない。

#### 埋め込み方

- 埋め込み位置は、その図を説明している**章の中**。
- `<svg>` 要素をそのまま本文に書く。前後を空行で挟み、**コードフェンスで囲まない**。
- 根要素の `xmlns="http://www.w3.org/2000/svg"` を必ず残し、**埋め込む側にだけ** `style="max-width:100%;height:auto"` を足す。
- 図の直後に `[図を SVG で開く](img/<ファイル名>.svg)` を 1 行添える。
- 図の直前か直後に、**その図が何を示しているかを 1 行**書く。図だけ置かない。
- **インラインの中身は `.svg` ファイルから機械的にコピーする。** Markdown 側の SVG を手で編集しない。

## 4. 検証と報告

出力前に自己点検する:

- [ ] **すべてのブロックに信頼区分が付いているか**（1 つでも未分類が無いか）
- [ ] **すべてのブロックにトークン上限と切り詰め順位が付いているか**
- [ ] **信頼できないブロックすべてに、最低 1 つのガードが対応しているか**
- [ ] **信頼できないブロックが 0 件になっていないか**（入力の出どころを辿り直したか）
- [ ] **トークン予算の検算が数値で書かれているか**（入力合計 + 出力上限 ≤ コンテキスト長）。コンテキスト長が未定なら、相対配分で設計し未決に上げたか
- [ ] 1 回の呼び出し × 反復上限が、オーケストレーション設計のコスト上限に収まるか
- [ ] **削ってはいけないブロック**が明示されているか。切り詰めが起きたことを記録する仕組みがあるか
- [ ] **キャッシュ境界が明示され、境界より前に可変要素が混ざっていないか**
- [ ] 信頼できない入力が、役割の指示・出力スキーマより**後ろ**に置かれているか
- [ ] **「インジェクションを防げる」と書いていないか。** 防げない範囲をリスクに上げたか
- [ ] 出力スキーマを**この設計書で別に定義していないか**（オーケストレーション設計のツール定義と同一か）
- [ ] 入れてはいけない情報が列挙され、**どのブロックで排除するか**が書かれているか
- [ ] 個人識別情報・鍵・他案件のデータをコンテキストに入れていないか
- [ ] 会話履歴の扱いが決まっているか（既定は保持しない）
- [ ] 評価の入力に**インジェクションを試すもの**が含まれているか。合格基準が「スキーマ適合・検証通過」になっているか（文章の良し悪しになっていないか）
- [ ] `context-templates.md` の全エージェントが `agent-definitions.md` の一覧と一致しているか（過不足が無いか）
- [ ] 各エージェントのブロック構成が、`agent-definitions.md` の**プロンプト方針（含める／含めない）に反していないか**
- [ ] 上流 ID を振り直していないか、`CTX` / `CG` / `CQ` / `CR` の ID が重複していないか
      （`grep -oE '\b(CTX|CG|CQ|CR)-[0-9]{3}\b' "$DOCS_DIR"/agent-context/*.md | sort | uniq -c` で確認）
- [ ] **プロンプトの本文を書いていないか**（構造・順序・上限・規則だけになっているか）
- [ ] 出力が Markdown（`.md`）で、見出しレベル・テーブル記法が崩れていないか
- [ ] 保存先が `$DOCS_DIR/agent-context/` になっているか（リポジトリ内の `docs/` に書いていないか）
- [ ] **SVG がすべて `$DOCS_DIR/agent-context/img/` に保存されているか**（`agent-context/` 直下に `.svg` を置いていないか）
- [ ] **作成した SVG がすべて `agent-context.md` にインラインで埋め込まれているか**（`grep -c '<svg ' agent-context.md` と `ls img/*.svg | wc -l` が一致するか）
- [ ] 埋め込んだ SVG が `.svg` ファイルと同じ内容か（`style` 属性の追加以外に差分が無いか）
- [ ] **SVG が well-formed か**（`xmllint --noout "$DOCS_DIR"/agent-context/img/*.svg`。無ければ `python3 -c "import xml.etree.ElementTree as E;E.parse('<path>')"`）
- [ ] **図のトークン数・ブロック名が設計書の表と一致しているか**（概数にしていないか）
- [ ] 線が交差していないか。棒人間で描いたアクターがすべて人間か
- [ ] Mermaid の構文が正しいか（`npx` が使えるなら `npx -y @mermaid-js/mermaid-cli -i <入力>.md -o <スクラッチパッド>/check.md` で確かめる。使えなければ目視確認し、未検証であることを報告に書く）

最後にユーザーへ短く報告する:

- 作成・更新したファイル（**フルパスで示す**。設計書 / 構成カタログ / `img/` 配下の図）
- ブロック数（信頼できる／できない の内訳）・ガード数・エージェント別テンプレートの数
- 図の枚数と、分割した場合はその方針
- **トークン予算の検算結果**（合計とコンテキスト長。未定なら相対配分である旨）
- **信頼できない入力とガードの対応**（1 つでも未対応があれば必ず報告する）
- **インジェクションについて防げない範囲**（「防げる」と報告しない）
- 主要な設計判断と、**「仮」のまま残したもの**
- **未決事項の一覧**（`CQ` と、上流へ差し戻した `Q` / `AQ` / `OQ`。ユーザーの回答が必要なものを箇条書きで）

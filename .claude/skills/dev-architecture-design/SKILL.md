# dev-architecture-design

確定した要件を、**何を作るか（コンポーネント）と、どう繋ぐか（インターフェース）に落とす**スキル。

ここでは**要件を新しく発掘しない**。要件に書かれていないことが必要になったら、推測で埋めずに未決事項へ上げ、必要なら `dev-requirements-analysis` / `dev-requirements-spec` に差し戻す。

## 0. 作業ディレクトリ

**読み取り先・保存先はどちらも次のディレクトリ**（リポジトリ内の `docs/` ではない）:

```bash
DOCS_DIR=/mnt/c/second-brain/ethglobal_hackathon/docs
```

- 入力資料: `$DOCS_DIR/` 配下（とくに `$DOCS_DIR/requirements/`）
- 出力先: `$DOCS_DIR/architecture/`（Markdown）／`$DOCS_DIR/architecture/img/`（**アーキテクチャ図の SVG はすべてここに置く**）
- このディレクトリは **Obsidian の vault**（Windows 側 `C:\second-brain`）を WSL からマウントしたもの。以下に注意する:
  - `.obsidian/` 配下と `*:Zone.Identifier` は入力から除外する。
  - 改行は LF、文字コードは UTF-8 で書く。
  - Obsidian で開けるよう、**見出し・テーブル・チェックリスト・Mermaid ブロックは標準の Markdown 記法**に収める。
- **解析対象から除外するファイル**（ユーザー指示 2026-09-25。読み込まない・出典にも使わない）:
  - `01-アーキテクチャ図.svg`
  - `02-アーキテクチャ図-WorldMiniApp案.svg`
  - `ETH_Globalユースケース.pdf`
  ユーザーが明示的に「この資料も見て」と指定した場合にだけ読む。その場合は使ったことを報告する。
  - **このスキルにとっては注意が要る除外指定**で、除外リストに既存のアーキテクチャ図案が 2 つ含まれている。**既存案を踏まえた設計にしたいかどうかを、着手前にユーザーへ 1 度だけ確認する**（確認せず勝手に読まない／勝手に無視して作り直さない）。
- ディレクトリが存在しない／アクセスできない場合は、勝手に別の場所へ書かず、ユーザーにパスを確認する。
- ユーザーが `docs/xxx.md` のような相対パスを渡した場合は、**`$DOCS_DIR` 起点として解決する**。

## 1. 入力を読む

| 入力 | 扱い |
|------|------|
| `$DOCS_DIR/requirements/requirements.md` | **一次入力**。ここにある要件 ID・優先度・制約・未決事項をそのまま引き継ぐ |
| `$DOCS_DIR/requirements/requirements-traceability.md` | 要件 ID の全量と状態（確定/仮/要確認）を控え、対応表の土台にする |
| `$DOCS_DIR/requirements/analysis.md` | 矛盾・リスク・スコープ外の背景を確認する |
| `$DOCS_DIR/architecture/` の既存ファイル | 差分更新のために必ず読む |
| `$DOCS_DIR/` 配下のその他資料 | 技術的な前提の裏取りに使う |

- `requirements.md` が無い場合は、**先に `dev-requirements-spec` を実行するようユーザーに促す**。それでも進める場合は、ある資料だけで設計し、「前提・参照資料」に**要件定義書なしで作成した**ことを明記する。
- **要件 ID（BR / UC / FR / NFR / CON / OUT / Q / R）は絶対に振り直さない。** 過不足があれば要件側に戻して直す。
- 要件の状態が `仮` / `要確認` のものは、**それに依存する設計判断も `仮` として扱う**。確定扱いにしない。

とくに次の 4 つを重点的に読む。アーキテクチャを決めるのはここだから:

1. **NFR（非機能要件）** — 性能・可用性・セキュリティ・プライバシー・運用監視・拡張性・法規制。構成を決めるのは機能要件ではなく、ほぼこれ。
2. **CON（制約）** — 技術スタック・外部サービス・チェーン・予算・期限。選択肢を先に狭める。
3. **外部インターフェースの章** — 連携先が確定しているか、方式が未定か。
4. **データ要件の章** — 正本の置き場所。ここが未定なら設計は詰められない（未決に上げる）。

## 2. 設計する

次の順で進める。**飛ばさない。**とくに 1 と 2 を飛ばすと、根拠のない構成図ができる。

### 2-1. 設計ドライバを拾う

「この要件があるから、この構成になる」と言えるものだけを拾い、表にする。Must の FR、全 NFR、全 CON が対象。**設計に影響しない要件は書かない。**

### 2-2. システム境界を引く

**何を作り、何を作らないか**を先に決める。

- 要件定義書の「アクター一覧（外部システム）」「外部インターフェース」「スコープ外（OUT）」を起点にする。
- 境界の内側＝自分たちで実装するもの。外側＝既にあるもの・他者が運用するもの。
- **境界が要件と食い違う場合は、勝手に決めずに未決事項へ上げる**（例: あるコンポーネントが「システムの一部」か「外部のアクター」か要件側で未確定）。

### 2-3. 責務をコンポーネントに割り当てる

- **1 コンポーネント = 1 責務。** 「〜を管理する」で終わる曖昧な責務名にしない。何を入力に何を出すかで書く。
- 各コンポーネントに `CMP-001` から採番する。
- **すべての Must の FR が、いずれかのコンポーネントに割り当たっている**こと。割り当たらない FR は、設計漏れか、要件側の問題。どちらかを明記する。
- 要件に無い機能をコンポーネントに足さない。必要だと気づいたら要件側へ差し戻す。

### 2-4. データの配置を決める

要件定義書の「データ要件」と整合させる。**正本（source of truth）がどこにあるか**を、データごとに 1 つに定める。

- 外部サービスやオンチェーンが正本のデータは、自分たちのストアには**参照用の識別子だけ**を持つのが基本。複製する場合は「キャッシュである」ことと、不整合が起きたときにどちらを正とするかを書く。
- **一度書いたら消せない置き場所（オンチェーン等）に何を置くか**は、プライバシー要件と削除要求への対応に直結する。要件側が未定なら、ここで決めずに未決へ上げる。

### 2-5. インターフェースを定義する

コンポーネント間と外部連携のすべてに `IF-001` から採番し、次を書く:

- 呼び出し元 → 呼び出し先（**向き**を必ず書く）
- 同期 / 非同期
- 方式（HTTP+JSON、オンチェーン呼び出し、イベント購読 など）
- 認証方式
- 根拠になる要件 ID

**依存の向きを循環させない。** 循環したらコンポーネントの切り方が間違っている。切り直す。

### 2-6. 横断的関心事を決める

次はどのコンポーネントにも関わるので、個別ではなく方針として 1 度決める。**要件に記述が無いものは、推測で決めずに未決事項へ上げる**（「決めていない」と書くこと自体が設計の成果物）。

- 認証 / 認可（誰が何をしてよいか）
- 監査ログ（何を・どこに・どれだけ残すか）
- 通知（誰に・いつ）
- エラー処理とリトライ、**冪等性**（同じ要求が 2 回来たらどうなるか）
- 秘密情報の管理（鍵・トークンの置き場所）
- 障害時の縮退（外部サービスが落ちたら何が止まり、何が動くか）

### 2-7. 非機能要件への対応を書く

**NFR を 1 件ずつ**「どの設計要素で満たすか」に落とす。満たせないものは、そう書いてリスクに上げる。「がんばる」は書かない。

### 2-8. 技術選定と代替案

- 制約（CON）で決まっているものは、それに従う。**選定ではなく制約であることを明記する。**
- 制約で決まっていないものを選ぶときは、**必ず代替案と比較して ADR に残す**。比較軸は、その案件の NFR から取る（一般論の優劣で選ばない）。
- 要件から決められないものは **「仮」と明記して未決事項へ上げる**。仮のまま断定しない。

### 2-9. ID の採番

| 対象 | ID | 備考 |
|---|---|---|
| コンポーネント | `CMP-001` | 境界の内側・外側の両方に振る（外部は「外部」と明記） |
| インターフェース | `IF-001` | コンポーネント間・外部連携のすべて |
| 設計判断 | `ADR-001` | 1 判断 1 件 |
| アーキテクチャ上のリスク | `AR-001` | 要件側の `R-nnn` とは別系列 |
| アーキテクチャ上の未決事項 | `AQ-001` | 要件側の `Q-nnn` とは別系列 |

- **要件側の欠落**を見つけた場合は `AQ` ではなく、**要件側に `Q-nnn` を追加して差し戻す**（`analysis.md` と `requirements.md` の両方を更新し、それぞれの変更履歴に書く）。`AQ` は「要件は決まっているが設計の選択が残っている」ものに使う。
- 既存の `architecture.md` がある場合は必ず先に読み、**既存の ID を再利用して振り直さない**（廃止する要素は行を残して「廃止」と記す）。新規分だけ最大番号の続きから採番する。

## 3. 出力する

**設計書は必ず Markdown（`.md`）で、アーキテクチャ図は必ず SVG（`.svg`）で作成する。** 他形式では出力しない（ユーザーから明示的に別形式を指定された場合のみ、Markdown / SVG を正本として作ったうえで変換する）。

出力先は **`$DOCS_DIR/architecture/`**（リポジトリ内の `docs/` には書かない）。**SVG は `img/` サブディレクトリに置く。** 無ければ作成する:

```bash
mkdir -p "$DOCS_DIR/architecture/img"
```

出力は次の 3 点 + 図:

| ファイル | 内容 |
|---|---|
| `architecture.md` | アーキテクチャ設計書（図はここにインライン埋め込み） |
| `architecture-decisions.md` | 設計判断記録（ADR） |
| `architecture-traceability.md` | 要件 ↔ コンポーネント / インターフェース の対応表 |
| `img/*.svg` | アーキテクチャ図（3-4 参照） |

既存ファイルがあれば内容を読み、上書きではなく **差分更新** とし、変更点を「変更履歴」に追記する。

Markdown の書き方ルール:

- 見出しは `#`（文書タイトル）→ `##`（章）→ `###`（節）の順に、レベルを飛ばさずに使う。
- 一覧は **GFM のテーブル**で書く。セル内改行は `<br>`、セル内の `|` は `\|` にエスケープする。
- **構造の図（コンテキスト・コンテナ・コンポーネント・デプロイ）は SVG。** ファイルに保存し、中身を `architecture.md` にインラインで埋め込む（3-4）。
- **振る舞いの図（シーケンス・状態遷移）は Mermaid** のコードブロック（```` ```mermaid ````）で書く。SVG で手描きしない。
- 画像は `architecture/img/` 配下の自前ファイルのみ参照する（`architecture.md` からは `img/<ファイル名>.svg` の相対パス）。外部 URL の画像は使わない。
- 装飾のための HTML は使わない（`<br>` と埋め込み `<svg>` を除く）。

### 3-2. `$DOCS_DIR/architecture/architecture-decisions.md`（ADR）

1 判断 1 レコード。**採用案だけでなく、却下した案と却下理由を必ず残す**（後から「なぜこうしたか」を辿れるようにするのが目的）。

```markdown
# アーキテクチャ設計判断記録（ADR）

> 最終更新: YYYY-MM-DD

## ADR-001 <決定の要約（体言止め）>

- **状態**: 採用 / 仮採用 / 保留 / 却下 / 見直し
- **日付**: YYYY-MM-DD
- **文脈**: どの要件・制約から、この判断が必要になったか（要件 ID を書く）
- **選択肢**
  | 案 | 概要 | 長所 | 短所 |
- **決定**: どれを採ったか
- **根拠**: どの NFR / CON に照らして、その案が勝ったか
- **トレードオフ**: この決定で捨てたもの、将来効いてくる制約
- **影響する要件**: FR-00x, NFR-00x
- **見直す条件**: 何が変わったらこの判断をやり直すか
```

### 3-3. `$DOCS_DIR/architecture/architecture-traceability.md`（対応表）

要件がどこで実現されるかを 1 表にする。**この表の価値は「埋まっていない行」にある**ので、未割当を隠さない。

```markdown
# 要件 ↔ アーキテクチャ 対応表

> 最終更新: YYYY-MM-DD

| 要件ID | 種別 | 優先度 | 要件（1文） | 実現するコンポーネント | 関連IF | 関連ADR | 状態 |
|---|---|---|---|---|---|---|---|

## カバレッジ
| 種別 | 全件 | 割当済 | 未割当 |

## 未割当の要件
| 要件ID | 未割当の理由（設計漏れ / スコープ外 / 未決事項待ち） |
```

- 状態は `設計済` / `仮` / `未着手` / `対象外` のいずれか。
- **Must の FR に未割当があるまま「設計完了」と報告しない。**

### 3-4. アーキテクチャ図（SVG）

**構造の図は必ず SVG で作成し、`$DOCS_DIR/architecture/img/` に保存したうえで、その中身を `architecture.md` にインラインで埋め込む。** 画像リンクによる参照だけで済ませない — Markdown 単体で図が見える状態にする。

#### 作る図

| ファイル名 | 図 | 何を示すか | 作らなくてよい場合 |
|---|---|---|---|
| `01-system-context.svg` | システムコンテキスト図 | 対象システムを 1 つの箱として、人間のアクターと外部システムとの関係 | **必ず作る** |
| `02-container.svg` | コンテナ図 | 実行単位（アプリ・API・ワーカー・データストア・コントラクト等）と、その間の通信 | **必ず作る** |
| `03-component-<名前>.svg` | コンポーネント図 | 1 つのコンテナの内部構造 | 内部を分解しなくても実装できるコンテナ |
| `04-deployment.svg` | デプロイ図 | 実行環境・ネットワーク境界・どこに何が載るか | 実行環境が 1 つしかなく、コンテナ図と同じ絵になる場合 |
| `05-<主題>.svg` | 補助図 | 責務分担・信頼境界など、上記で表せない構造 | 上記で足りる場合 |

図ありきで作らない。**表で足りるなら作らない。** ただし `01` と `02` は必ず作る。

#### 記法

| 要素 | 記法 |
|---|---|
| 対象システム（境界） | 太めの角丸矩形。上部中央にシステム名。コンテキスト図では 1 つの箱、コンテナ図では中にコンテナを並べる |
| コンポーネント / コンテナ | 角丸矩形。中に `CMP-001` と名称、その下に技術名を小さく（例: `Next.js` / `Solidity`）。技術が仮なら `（仮）` を付ける |
| 外部システム | 角丸矩形 + `«system»` のステレオタイプ。塗りを変えて区別する |
| データストア | 角丸矩形 + `«datastore»`。円筒で描いてもよい |
| 人間のアクター | 棒人間 + 直下に名称 |
| 同期の通信 | 実線 + 矢印。**向きを必ず付ける** |
| 非同期の通信 | 破線 + 矢印 |
| 信頼境界 / ネットワーク境界 | 破線の矩形 + 左上にラベル |
| 凡例 | 図の下部に必ず置く |

- **人間でないものを棒人間で描かない。** 認証サービス・ブロックチェーン・スマートコントラクト・AI エージェントは利用者ではないので、棒人間で描くと「ユーザー」に読み違えられる。角丸の箱 + ステレオタイプで描く。
  - 判断基準: **その相手は画面を操作したり意思決定をしたりする人間か？** いいえなら箱にする。
- 線には**何が流れるか**をラベルで書く（例: `依頼を登録 / HTTPS+JSON`）。無地の線を引かない。
- 設計書の表と **ID・名称を完全に一致**させる。図だけの略称を作らない。

#### レイアウト規則

- **依存の向きを揃える**（上から下、または左から右）。逆流する線があれば、それは設計の匂いなので構成を見直す。
- 人間のアクターは外側（上端か左端）、外部システムはその反対側にまとめる。
- **線を交差させない。** 交差しそうならノードの並び順を入れ替える。
- ノードが 20 を超えて読めなくなる場合は、**上位だけを描くか領域ごとに分割**する。全部を 1 枚に詰めない。

#### SVG の書き方（必須ルール）

- ルートは `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 W H" width="W" height="H">`。`viewBox` を必ず付ける。
- **ダーク/ライト両対応**: 背景に `<rect fill="#ffffff">` を敷き、線と文字は濃色（`#1f2937`）で描く。`currentColor` や CSS 変数に頼らない。
- フォントは `font-family="'Noto Sans JP','Hiragino Sans','Yu Gothic',sans-serif"`、本文 `font-size="12"`〜`13`。テキストは `<text>` 要素で書き、パス化しない。
- `<style>` 要素は使わず、すべて属性で指定する（Obsidian と GitHub の描画差を避けるため）。
- **SVG の中に空行を入れない**（コメントや要素のまとまりの間も詰める）。Markdown では HTML のかたまりが空行で終わるため、インラインで埋め込んだ `<svg>` が途中で切れて表示されなくなる（2026-09-26 に as-built と実装記録で発生）。
- 矢印は `<defs>` の `<marker>` を定義して再利用する。**`id` は図ごとに一意にする**（同じ Markdown に複数の SVG を埋めると id が衝突するため）。
- `«` `»` や `<<include>>` のような記号をテキストに書くときは、**必ず実体参照でエスケープする**（`&#171;` `&#187;` / `&lt;&lt;` `&gt;&gt;`）。生で書くと XML として壊れる。
- 手書きで組み立てる。作図ツールの巨大な出力を貼り付けない。

#### 埋め込み方

- 埋め込み位置は、その図を説明している**章の中**。
- `<svg>` 要素をそのまま本文に書く。前後を空行で挟み、**コードフェンスで囲まない**。
- 根要素の `xmlns="http://www.w3.org/2000/svg"` を必ず残し、**埋め込む側にだけ** `style="max-width:100%;height:auto"` を足す。
- 図の直後に `[図を SVG で開く](img/<ファイル名>.svg)` を 1 行添える（GitHub はインライン SVG を表示しないため）。
- 図の直前か直後に、**その図が何を示しているかを 1 行**書く。図だけ置かない。
- **インラインの中身は `.svg` ファイルから機械的にコピーする。** Markdown 側の SVG を手で編集しない（2 か所が食い違うため）。図を直すときは `.svg` を直してからコピーし直す。

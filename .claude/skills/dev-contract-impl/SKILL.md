# dev-contract-impl

設計したオンチェーンの構造を、**動くコントラクトにする**スキル。

**このスキルが扱うものは、デプロイしたら戻せない。** 他のどの実装よりも、出す前の確認を厚くする。

扱う範囲:

- Escrow コントラクトの実装（struct / mapping / enum / event / 関数 / アクセス制御）
- テスト（正常系・不正系・**不変条件**・**イベントからの再構築**）
- ガスの計測
- テストネットへのデプロイと、ソースの検証公開

**扱わない範囲**（別のスキル）:

- ENS への登録・subname 作成・テキストレコードの書き込み → **バックエンドの実装**（CMP-008 がコントラクトを呼ぶ側であり、自前のコントラクトではない）
- 投影テーブルの構築、イベントの購読 → **バックエンドの実装**（CMP-009）

## 0. 作業ディレクトリ

**コードと設計記録で置き場所が違う。混ぜない。**

```bash
REPO=/home/million/team_codrea_ethglocal          # コード・テスト・ABI・デプロイ設定
DOCS_DIR=/mnt/c/second-brain/ethglobal_hackathon/docs   # 設計書（読む）・実装記録（書く）
```

| 種類 | 置き場所 |
|---|---|
| Solidity のソース・テスト・ビルド設定 | **`$REPO`**（`contracts/` 配下） |
| ABI・デプロイしたアドレスの記録 | **`$REPO`** |
| 設計書（入力） | `$DOCS_DIR`（読むだけ。**このスキルで設計書を書き換えない**） |
| 実装記録（設計との対応・逸脱・ガス・デプロイ結果） | **`$DOCS_DIR/implementation/`** |

- `$DOCS_DIR` は **Obsidian の vault**。改行は LF、文字コードは UTF-8。見出し・テーブルは標準の Markdown 記法に収める。
- **`$REPO/docs/` は vault ではない。** リポジトリ側の `docs/` には既存の資料（アーキテクチャ図の案・PDF）が置かれている。**ここに設計記録を書かない。**
- **秘密鍵・ニーモニック・API キーをリポジトリに置かない。** `.env` を作る場合は `.gitignore` に入れ、`.env.example` にはプレースホルダだけを書く。
- **解析対象から除外するファイル**（ユーザー指示 2026-09-25）: `01-アーキテクチャ図.svg`、`02-アーキテクチャ図-WorldMiniApp案.svg`、`ETH_Globalユースケース.pdf`。ユーザーが明示的に指定した場合にだけ読む。

## 1. 入力を読む

| 入力 | 扱い |
|------|------|
| `$DOCS_DIR/database/database-design.md` の **6 章** | **一次入力**。struct・mapping・enum・event・値の型と精度。**ここに書かれた形をそのまま実装する** |
| 同 **5-3 章**（列挙値） | オフチェーンの `escrow_status` と**序数が一致している**ことを確認する |
| 同 **7 章**（正本と同期） | イベントから投影を再構築できるか、テストで確かめる対象 |
| `$DOCS_DIR/architecture/architecture-decisions.md` | ADR-001（資金の正本はオンチェーン）・ADR-006（書き込みの集約） |
| `$DOCS_DIR/agent-orchestration/agent-orchestration.md` | GRD-009〜011（送金の条件）。**どこまでをコントラクトで判定するか**の境界 |
| `$DOCS_DIR/requirements/requirements.md` | NFR-003・FR-007・FR-012・FR-013・FR-019・FR-034・CON-003・CON-006 |
| `$REPO` の既存コード | あれば必ず読む。**既存の関数シグネチャを勝手に変えない** |

- `database-design.md` が無い場合は、**先に `dev-database-design` を実行するようユーザーに促す**。
- **設計書の ID（CMP / IF / FR / NFR / GRD / DQ など）は振り直さない。**

## 2. 着手前に確認する

**実装を始める前に、形が変わる未決事項が残っていないかを必ず確認する。** 残っているものは一覧にしてユーザーへ示し、**進めてよいかを確認する**。推測で埋めて実装しない。

とくに次は、**残ったまま作ると作り直しになる**:

| 確認すること | 決まっていないと何が起きるか |
|---|---|
| 決済トークン | `token` の扱い（ネイティブか ERC20 か）と、金額の単位が決まらない |
| 対象チェーン | デプロイ先が決まらない。ガスの見積りも意味を持たない |
| 「承認」の正本の所在 | 承認をコントラクトで数えるのか、オフチェーンの記録を正とするのかで**関数の構成が変わる** |
| アップグレード方式 | プロキシを使うなら**最初から**その形で書く必要がある。後から変えられない |
| 検収のタイムアウト時の既定動作 | 自動承認か自動返金かで、コントラクトに持たせる関数が変わる |

**進めてよいと言われた場合は、仮置きした内容を実装記録に明記する。** 何を仮定して作ったかが後から分かるようにする。

## 3. ツールチェーンを決める

- **既存の設定があればそれに従う**（`foundry.toml` / `hardhat.config.*` / `package.json`）。勝手に乗り換えない。
- 無い場合は、**この環境で実際に動くものを選ぶ**。選ぶ前に確認する:

```bash
for c in forge cast anvil solc npx node; do printf '%-6s ' "$c"; command -v $c >/dev/null && echo あり || echo なし; done
```

- **入っていないものを前提にしない。** ネットワークからの導入が必要なら、導入してよいかをユーザーに確認する。
- 選んだ理由を実装記録に 1 行書く。**一般論で選ばない**（この環境で動くか、テストが書きやすいか、で選ぶ）。

## 4. 実装する

### 4-1. 設計からの逸脱を禁じる

**次は設計書のとおりに実装する。変えたくなったら、実装側で変えずに上流へ差し戻す。**

- `struct` のフィールド名・型・並び
- **`enum` の値と順序**（序数で永続化され、オフチェーンの列挙型と対応している。**順序を変えると投影が壊れる**）
- `event` の名前・引数・`indexed` の指定
- 識別子の生成規則（`keccak256` の入力の並び）
- 金額・時刻の型

逸脱が避けられない場合は、**実装を止めて上流のどの記述と食い違うかを報告する**。勝手に直さない。

### 4-2. 書く順序

1. **型**（enum → struct）
2. **状態**（mapping。設計書にあるものだけ。**便利そうな mapping を足さない**）
3. **イベント**（設計書の 8 件をそのまま）
4. **エラー**（`revert` の理由。文字列ではなくカスタムエラーを使う。**文字列はガスを食う**）
5. **アクセス制御**（誰がどの関数を呼べるか。ADR-006 の「書き込みの集約」に従う）
6. **関数**（状態遷移を進めるもの）
7. **参照用の getter**（投影との突き合わせに使う。データ設計 7 章の「突き合わせ」で要る）

### 4-3. 守ること

- **ストレージに文字列と可変長配列を置かない**（設計書の方針）。長い値はハッシュか、オフチェーンの識別子にする。
- **金額に浮動小数を使わない。** 整数のまま扱う。
- **外部への送金は状態を更新してから行う**（再入可能性への対処）。
- **`revert` の理由をカスタムエラーで表す。** どの条件で落ちたかがテストとオフチェーンから判別できること。
- **アクセス制御を全ての状態変更関数に付ける。** 付けない関数がある場合、その理由を書く。
- **設計書に無い機能を足さない。** 「あると便利」で関数を増やさない。

## 5. テストする

**次の 4 種類をすべて書く。1 つでも欠けたら完了にしない。**

### 5-1. 正常系

設計書の主要フローをそのままなぞる。預託 → 成果物の提出 → 承認 → 自動支払い、および 条件未達 → 保留 → 紛争 → 解放。

### 5-2. 不正系

**通ってはいけない呼び出しが、確実に落ちること**を示す。最低限:

- 権限のない者からの呼び出し
- 同じ承認者による二重の承認
- 同じタスクへの二重の預託
- 金額 0、必要承認数 0 の預託
- 預託されていないタスクへの承認・支払い
- 状態が合わない遷移（支払い済みのものへの再支払い、など）

### 5-3. 不変条件

**要件がコントラクトで守られていることを、テストで示す。** 最低限:

- **承認条件を満たさない限り、資金がコントラクトから出ない**（NFR-003）。ランダムな順序で操作しても破れないこと。
- 預託した総額と、支払い・返金・解放の総額が一致すること（資金が増えも減りもしない）。
- 承認数が必要承認数を超えないこと。

### 5-4. イベントからの再構築

**データ設計 7 章の「投影テーブルはイベントだけから再構築できる」という主張を、テストで確かめる。**

- 一連の操作を実行し、**発生したイベントだけ**から状態を組み立てる。
- 組み立てた状態が、コントラクトの getter が返す値と一致することを確認する。
- 一致しない項目があれば、**イベントの設計が足りない**。上流（データ設計 6-2）へ差し戻す。

これを通さずにバックエンドの実装へ進まない。**通らないまま進むと、投影の不整合として後から現れる。**

## 6. ガスを測る

- **1 タスクあたりの預託・承認・支払いのガスを測って記録する。**
- 契約と預託が**タスク単位**であるため（CON-006）、1 案件のガスは「タスク数 × 1 タスクあたり」になる。**案件あたりの概算も出す。**
- 設計書がガスの懸念をリスクとして挙げている場合、**実測値をそのリスクの行に紐づけて報告する**。

## 7. デプロイする

**デプロイしたら戻せない。** 次の順に進め、飛ばさない。

### 7-1. 出す前の確認

- [ ] 5 章のテストが**すべて通っている**
- [ ] `enum` の値と順序が、オフチェーンの列挙型（データ設計 5-3）と**一致している**
- [ ] `event` の署名が設計書（6-2）と**一致している**
- [ ] 識別子の生成規則が設計書（6-3）と**一致している**
- [ ] アップグレード方式の判断が済んでいる（未決なら、**アップグレードできない前提で出すことの合意**）
- [ ] デプロイに使う鍵が**テストネット用**であること（本番の鍵を開発環境で使っていない）

### 7-2. テストネットへ出す

- **必ずテストネットに先に出す。** いきなり本番へ出さない。
- デプロイしたアドレス・チェーン・ブロック高・デプロイに使ったコミットを記録する。
- **ソースを検証公開する**（第三者が中身を確認できること。要件の透明性に対応）。

### 7-3. 本番へ出す

- **ユーザーの明示的な指示があるまで本番へ出さない。**
- 出す前に 7-1 をもう一度確認する。
- 出したあと、アドレスを実装記録とバックエンドの設定に反映する。

## 8. 出力する

### 8-1. リポジトリ（コード）

```

$REPO/contracts/script/   # デプロイ用（鍵を含めない）
$REPO/contracts/out/      # ABI（ビルド生成物。追跡するかは判断して書く）
$REPO/.env.example        # プレースホルダのみ
```

- `.gitignore` に `.env`・ビルド生成物・依存を入れる。
- **コミットは求められたときだけ行う。** 勝手に push しない。

**`$DOCS_DIR/implementation/contract-impl.md`** に次を書く。無ければディレクトリを作る。

## 9. 検証と報告

出力前に自己点検する:

- [ ] **コードが `$REPO` に、実装記録が `$DOCS_DIR/implementation/` にあるか**（逆になっていないか）
- [ ] **`$REPO/docs/` に設計記録を書いていないか**（vault と混同していないか）
- [ ] **秘密鍵・ニーモニック・API キーをリポジトリに置いていないか。** `.env` が `.gitignore` に入っているか
- [ ] **設計書を書き換えていないか**（このスキルは設計書を読むだけ）
- [ ] struct・enum・event・識別子の生成規則が設計書と**一致しているか**。逸脱があれば記録し、上流へ差し戻したか
- [ ] **enum の序数がオフチェーンの列挙型と一致しているか**
- [ ] 設計書に無い状態変数・関数・イベントを足していないか
- [ ] ストレージに文字列や可変長配列を置いていないか
- [ ] 金額を整数で扱っているか
- [ ] すべての状態変更関数にアクセス制御があるか（無い場合、理由を書いたか）
- [ ] `revert` の理由がカスタムエラーで表されているか
- [ ] **5 章の 4 種類のテストがすべて書かれ、通っているか**
- [ ] **不変条件テストで NFR-003 を示せているか**（承認条件未充足での出金が 0 件）
- [ ] **イベントからの再構築テストが通っているか。** 通らない項目を残したまま先へ進んでいないか
- [ ] ガスを実測して記録したか。1 案件あたりの概算を出したか
- [ ] テストネットへ先に出したか。**本番へはユーザーの明示的な指示があったときだけ出したか**
- [ ] デプロイしたアドレス・チェーン・ブロック・コミットを記録したか。ソースを検証公開したか
- [ ] 実装記録の「設計からの逸脱」に、無い場合でも「無し」と書いたか
- [ ] 実装記録が Markdown（`.md`）で、見出しレベル・テーブル記法が崩れていないか
- [ ] コミット・push を、求められていないのに行っていないか

最後にユーザーへ短く報告する:

- 作成・更新したファイル（**フルパスで示す**。コードは `$REPO`、記録は `$DOCS_DIR/implementation/`）
- 実装したもの（関数の数・イベントの数）と、**選んだツールチェーンと理由**
- **設計との一致**（struct・enum・event・識別子）と、**逸脱の有無**（無ければ「無し」と明言する）
- **テストの結果**（種類ごとの件数と通過数）。とくに**不変条件**と**イベントからの再構築**の結果
- **ガスの実測値**と、1 案件あたりの概算
- デプロイの状況（**テストネットまでか、本番まで出したか**）
- **着手前に仮置きした未決事項**の一覧（何を仮定して作ったか）
- **戻せないもの**と、その影響

## 10. 後続への引き渡し

実装が通ったら、ユーザーに次を提案する（実行は求められたときだけ）:

- **`dev-database-impl`** — このコントラクトのイベントを受ける投影テーブルを実装する
- **`dev-backend-impl`** — イベントの購読・tx の送信・ENS の操作（CMP-008 / CMP-009）を実装する
- 実装中に設計の不足・矛盾が見つかった場合は、**`dev-database-design` / `dev-architecture-design` に戻して設計側を直す**（コントラクト側で辻褄を合わせない）

## 2026-09-25（1 日目）

### P-01 19:49 — コンセプト提示（開発開始）

**目的**: コンセプト図から MVP の仕様書を起こし、実装に入る前にスコープと未決事項を確定する。

**プロンプト**:
> このプロダクトを作ります。添付のコンセプト図 3 枚（World×ENS への訴求、開発するもの、サービス全体像）と、`docs/` にあるユースケース PDF・アーキテクチャ図をもとに、ETHGlobal Tokyo 提出用 MVP の仕様書を作成してください。
> AI Agent（PM Agent）が案件のタスク分解・チーム編成・実行・納品・支払いを進め、評価・仲裁・人間にしかできない作業は World ID で検証した人間が担い、Agent の名前と公開情報は ENS（ENSv2 / Sepolia）に置く構成です。
> 決めきれない点（親名、LLM、フレームワークなど）は私に質問し、回答を「決定事項」「未決事項」として仕様書に残してください。

**結果**: `dialogue-dev` スキルで要件を質問し、`docs/specs/20260925-agent-marketplace-mvp.md` を起草（コミット `f07f8ff`）。

### P-02 20:15 — ENS 親名の決定

**目的**: Agent を発行する ENS の親名を確定し、実装を進められるようにする。

**プロンプト**:
> ENS の親名はいったん `choice.eth`（Sepolia ENSv2）で進めてください。Agent は `<label>.choice.eth` の subname として発行し、仕様書の決定事項に記録してください。

**結果**: 仕様書「決定事項」に記録。以降 `<label>.choice.eth` で発行。

**結果**: 画面を拡張（コミット `7365a34`）。

### P-04 22:19 — 人員の ENS 管理と PM Agent による指名（追補 1 の起点）

**目的**: Human Task の担当者を公開募集だけに頼らず、受注側の会社が持つ人員から PM Agent が指名する仕組みにする。

**プロンプト**:
> Human Task について、受注側の会社の人員を ENS で管理する前提にしたいです。会社が所有する `.eth` の下に人員を subname として登録し、役割・スキル・拠点・稼働可否を text record に持たせてください。
> そのうえで、どの人員を Human Task に割り当てるかも PM Agent の役割にしてください。Human Task が生成されたら PM Agent が候補の ENS レコードを見て 1 名を指名し、本人が World ID で確認して受諾する。辞退や無応答なら次の候補に再指名し、候補が尽きたら従来の公開募集に落としてください。
> 仕様書に追補として記録し、検証基準も追加してください。

**結果**: 仕様書 追補 1（F9 / F10、V15〜V17）、会社と人員の登録画面、指名・辞退・再指名（コミット `f490a13`、`220d974`、`82ca79c`）。

### P-05 23:08 — ENS の実機確認

**目的**: ENSv2 Sepolia への書き込みが実際に動くことを、画面を介さず手動でも確かめられるようにする。

**プロンプト**:
> ENS の実装を Sepolia で実際に試したいです。親名の登録、リゾルバとサブレジストリの準備、Agent の subname 発行と text record の書き込みまでを実行できるセットアップスクリプトを用意してください。送信前に内容を確認できる dry-run も付けてください。
> あわせて、書き込んだ結果をレジストリとリゾルバから直接読んで確認するスクリプトと、手動で確認するための手順書（前提、必要な資金、確認方法、トラブルシュート）を `docs/` に置いてください。

**結果**: `scripts/ens_setup.py`（dry-run 付き）、`scripts/ens_check.py`、`docs/ens-manual-check.md`（コミット `b6a334f`）。人間が Sepolia ETH を送金し、`choice.eth` 登録と最初の Agent 公開を実施（手順書「実行記録」）。

### P-06 23:19 — アーキテクチャ設計書との相違確認

**目的**: 別途作成したアーキテクチャ設計書（CMP / IF / ADR）と現在の実装の差分を把握する。

**プロンプト**:
> 添付のアーキテクチャ設計書と現状の実装に相違がないか確認してください。コンポーネント・インターフェース・ADR ごとに、一致している点、異なる点、未実装の点を表にまとめてください。修正はまだ行わないでください。

**結果**: 差分表を提示。

### P-07 23:22 — 設計書への整合を決定（追補 2 の起点）

**目的**: 差分のうち資金の流れに関わるもの（工程単位の預託、承認による自動支払い、書き込みのワーカー集約）を設計書どおりにする。

**プロンプト**:
> 先ほどの差分表に基づき、実装をアーキテクチャ設計書に揃えてください。
> Escrow はタスク単位で預託し、承認者の EIP-712 署名が必要数そろったときにコントラクト自身が支払う構造にしてください。オンチェーンと ENS への書き込みはチェーン連携ワーカーに集約し、冪等キーと再送を持たせてください。World 検証は設計書が要求する 5 行為に広げてください。
> 意図的に設計書と変える点は、仕様書に「残差」として明記してください。

**結果**: Escrow の改修、ワーカー追加、World 検証 5 行為（コミット `37f3629`、`4c25220`、`b5e839c`）。仕様書 追補 2。

### P-08 23:44 — UI 方針

**目的**: デモで見せる画面の見た目を統一し、読みづらい折り返しをなくす。

**プロンプト**:
> UI を細部までブラッシュアップしてください。全画面を白黒基調のシンプルな見た目に統一し、バッジ、ボタン、数値と単位、アドレスや ENS 名などの等幅文字列が途中で改行されないようにしてください。余白、行間、表の揃えも見直してください。

**結果**: モノトーン統一、折り返し調整（コミット `ce9ce47`、`8f96617`）。

### P-23 12:45 — 実機で見つかった不具合の報告

**目的**: ブラウザからの Creator 公開（連続 tx）で発生した MetaMask のエラーを直す。

**プロンプト**:
> Creator 公開をブラウザから実行したところ、MetaMask で次のエラーが出ました（スクリーンショットとエラー全文を添付）。

**結果**: nonce の直列化と途中失敗からの再開（コミット `cd99d56`）。修正後に人間が再実行して完了を確認。

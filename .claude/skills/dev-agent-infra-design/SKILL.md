# dev-agent-infra-design

設計したエージェントを、**実際に動かすための基盤**を決めるスキル。

アーキテクチャの「デプロイ構成」は、どの実行環境に何が載るかの素描でしかない。本スキルは**そこに残された未決を決める場所**である。

設計するのは次の 10 個:

1. **実行基盤** — 何をどこで動かすか。同居させるか分離するか
2. **非同期ジョブ** — 非同期のインターフェースを何で実現するか
3. **同時実行とレート制限** — 何並列まで動かすか。外部の上限にどう合わせるか
4. **ネットワーク境界** — どこから入れて、どこへ出せるか
5. **秘密情報** — 鍵とキーをどこに置き、誰が読めるか
6. **可観測性** — 何をどこに記録するか
7. **環境の分離** — 開発・検証・本番で何を分けるか
8. **デプロイとロールバック** — 何を戻せて、何を戻せないか
9. **コスト上限の強制** — 上限を誰が止めるか
10. **停止手段と縮退** — 暴走時と外部障害時に何が起きるか

ここでは**コンポーネントもエージェントも新しく作らない**。上流の `CMP` / `AG` をどう配置するかだけを決める。

### 本スキルが決める上流の未決事項

上流に残っている未決のうち、**インフラの判断で決まるものはここで決める**。決められないものは理由とともに未決に残す。着手時に一覧を作ること。

| よくある例 | 本スキルで決まるか |
|---|---|
| コンポーネントを同居させるか分離するか、ネットワーク境界 | **決める** |
| 秘密鍵・API キーの保管方式 | **決める** |
| 実行トレースの保存先 | **決める** |
| チェーンのイベント取りこぼし・巻き戻しの再同期をどう動かすか | **決める**（方式が上流で決まっていれば、その実行基盤を決める） |
| 可用性の目標値 | **決めない**（業務判断。上流に残す） |
| コスト上限の数値 | **決めない**（誰が負担するかの判断。上流に残す）。ただし**上限を強制する場所**は決める |

## 2. 設計する

### 2-1. 実行単位を決める

上流のコンポーネントを、**実行される単位**に割り当てる。各単位に `INF-001` から採番する。

- **同居させるか分離するかを、理由とともに決める。** 規模が小さいうちは同居が正しいことが多い。「将来のため」で分けない。
- **分離する理由になるもの**: 秘密情報を持つ範囲を狭めたい／スケールの仕方が違う（常時 1 つ vs 並列に増やす）／障害の影響を切りたい／再起動の頻度が違う。
- 各実行単位に「**動かし方**」を決める: 常駐するのか、要求ごとに起動するのか、定期に起動するのか。

### 2-2. 非同期ジョブの実体を決める

上流のインターフェースのうち**非同期のもの**は、何かの上で運ばれる。それを決める。

- 何を使うか（キュー・ジョブテーブル・スケジューラ）と、**選んだ理由**。
- **重複実行が起きたときにどうなるか。** 上流が冪等キーを定めているなら、それをどこで判定するか。
- 失敗したジョブの扱い（再試行の回数・間隔・打ち切り後の行き先）。
- **順序が要るか**を明示する。要らないなら「要らない」と書く（要ると誤解されると構成が重くなる）。

### 2-3. 同時実行とレート制限

- **1 案件あたり・全体で何並列まで動かすか**を決める。
- **外部サービスの上限に合わせる。** LLM・チェーンの RPC・名前解決サービスには、それぞれ呼び出しの上限がある。**上限を超えたときに何が起きるか**（待つ・落とす・遅らせる）を決める。
- 上限に達したことを**検知できるようにする**（2-6）。
- **長時間の待ちを実行単位が抱え込まない。** 人間の判断待ちがある設計では、待っている間プロセスを占有しない作りにする（状態を外に出す）。

### 2-4. ネットワーク境界

- **入ってこられる経路**を列挙する。それ以外は塞ぐ。
- **出ていける先を列挙する。** エージェントは外部サービスを呼ぶため、**許可先を明示し、それ以外への通信を遮断する**。
  - これは**プロンプトインジェクションで外部へデータを送らせる攻撃**に対する、数少ない実効のある防御になる。上流で「インジェクションは防げない」としている場合、**出口の制限が被害を抑える最後の砦**になる。
- 公開する必要がないものを公開しない（データストア・ジョブ基盤・管理用の操作）。

### 2-5. 秘密情報

- **何が秘密か**を列挙する（鍵・API キー・接続情報）。
- **どこに置くか**と、**どの実行単位が読めるか**を決める。上流が「鍵を持つ範囲を限定する」と決めている場合、**その範囲を物理的に実現する**（読める実行単位を絞る）。
- **取り替え方（ローテーション）**を決める。取り替えられない設計にしない。
- **秘密をログ・トレース・プロンプトに出さない**ことを、どこで担保するか。

### 2-6. 可観測性

- **何を記録するか**を決める（上流の監査ログ要件・エージェントの実行トレース・コスト）。
- **どこに保存するか**を決める。上流で保存先が未定なら、**ここで決める**（それが本スキルの役割）。
- **保持期間**を決める。上流が未定なら仮置きして未決に上げる。
- **記録してはいけないもの**（個人識別情報・秘密）を、どこで落とすか。
- **アラート**: 何が起きたら人に知らせるか。**コスト上限への接近・停止手段の発動・外部サービスの停止**は最低限含める。

### 2-7. 環境の分離

- いくつの環境を持つか（開発・検証・本番）。**ハッカソン規模なら 2 つで足りることが多い。増やす理由を書く。**
- 環境ごとに**必ず分けるもの**: 秘密情報、外部サービスの接続先、データストア、**資金が動く先**。
- **本番の鍵と資金を、本番以外から触れないようにする。** これを満たさない構成を出さない。
- チェーンを使う場合、**環境ごとにネットワークを分ける**（検証用と本番用）。

### 2-8. デプロイとロールバック

- **何を、どの単位でデプロイするか。** ライフサイクルが違うものを一緒にしない。
  - 頻繁に変わるもの（プロンプト・エージェントの定義データ）と、めったに変えないもの（コントラクト）を分ける。
- **戻せるもの／戻せないもの**を表にする。**オンチェーンにデプロイしたものは戻せない**。戻せないものには、出す前の確認手順を置く。
- **設定だけを変えて挙動を変えられる範囲**を決める（再デプロイなしで止められるか等）。

### 2-9. コスト上限の強制

- 上流のコスト上限を、**誰が止めるか**を決める。
- **アプリケーション任せにしない。** 実行単位が暴走したときに、その実行単位自身が止まることは期待できない。**外側で止める場所**を用意する。
- 外部サービス側に上限設定の仕組みがあるなら使う（**二重に置く**）。

### 2-10. 停止手段と縮退

- 上流のキルスイッチを、**どこでどう実現するか**を具体的に決める。
  - 誰が操作できるか／効くまでの時間／**実行中のものにどう効くか**。
  - **再デプロイが必要な停止手段にしない。** 緊急時に間に合わない。
- 外部サービスが落ちたときに**何が止まり、何が動き続けるか**を表にする。上流で縮退方針が未定なら、**「決まっていない」と書いたうえで、現状の構成で何が起きるかは書く**（それは事実として判定できる）。

### 2-11. ID の採番

| 対象 | ID | 備考 |
|---|---|---|
| インフラ要素（実行単位・ジョブ基盤・ストア・境界・秘密の保管先） | `INF-001` | 上流の `CMP` との対応を必ず持たせる |
| 運用手順 | `OPS-001` | 停止・再開・鍵の取り替え・巻き戻しは最低限 |
| 設計上の未決事項 | `IQ-001` | 上流の `Q` / `AQ` / `OQ` / `CQ` とは別系列 |
| 設計上のリスク | `IR-001` | 上流の `R` / `AR` / `OR` / `CR` とは別系列 |

- **上流の未決を本スキルで決めた場合は、上流の該当行を「回答済（本スキルで決定）」に更新する**（該当ファイルと変更履歴の両方）。決めたまま上流を放置しない。
- 既存の設計書がある場合は必ず先に読み、**既存の ID を振り直さない**。

### 3-2. `$DOCS_DIR/agent-infra/infra-runbook.md`（運用手順書）

**緊急時に読まれる文書。** 説明ではなく**手順**を書く。

```markdown
# 運用手順書

> 最終更新: YYYY-MM-DD
> **緊急時はここだけを読めば操作できること。** 背景の説明は `agent-infra.md` に置く。

## OPS-001 <手順名>

- **いつ使うか**: 1 文
- **誰が実行できるか**
- **所要時間の目安**
- **手順**
  1. …
  2. …
- **確認方法**: 実行後に何を見れば成功と分かるか
- **戻し方**: 元に戻す手順（戻せない場合は「戻せない」と書く）
- **関連**: GRD-00x, INF-00x
```

最低限そろえる手順:

- **全体を止める / 案件単位で止める**（上流のキルスイッチに対応）
- **止めたものを再開する**
- **秘密を取り替える**（漏えい時を含む）
- **デプロイを戻す**（戻せないものは、その旨と代替手段）
- **取りこぼし・巻き戻しからの復旧**（チェーンを使う場合）

|---|---|
| 実行単位 | 角丸の矩形。中に `INF-001` と名称、下に動かし方（常駐／要求ごと／定期） |
| 載るコンポーネント | 実行単位の中に `CMP-00x` を列挙。**上流の ID と名称をそのまま使う** |
| **秘密を持つ実行単位** | 枠線を太くし、`«秘密あり»` を付ける（色だけに頼らない） |
| データストア | 角丸の矩形 + `«datastore»` |
| 外部サービス | 角丸の矩形 + `«external»` |
| ネットワーク境界 | 破線の矩形 + 左上にラベル（公開／非公開） |
| 許可する通信 | 実線 + 矢印。ラベルに用途 |
| **遮断する通信** | 破線 + 矢印の先に `&#215;`。**「塞いでいる」ことを図で示す** |
| 人間のアクター | 棒人間 + 直下に名称 |
| 凡例 | 図の下部に必ず置く |

- **人間でないものを棒人間で描かない。** 判断基準は「その相手は画面を操作したり意思決定をしたりする人間か？」。いいえなら箱にする。
- 図の中の ID・名称は**設計書の表と完全に一致**させる。

#### レイアウト規則

- 実行構成図は**外部を外側、自分たちの実行単位を内側**に置く。
- ネットワーク境界図は**入る方向を左、出る方向を右**に揃える。
- **線を交差させない。** 交差しそうならノードの並び順を入れ替える。
- 実行単位が 15 を超える場合は環境別・層別に分割する。

#### SVG の書き方（必須ルール）

- ルートは `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 W H" width="W" height="H">`。`viewBox` を必ず付ける。
- **ダーク/ライト両対応**: 背景に `<rect fill="#ffffff">` を敷き、線と文字は濃色（`#1f2937`）で描く。`currentColor` や CSS 変数に頼らない。
- フォントは `font-family="'Noto Sans JP','Hiragino Sans','Yu Gothic',sans-serif"`、本文 `font-size="12"`〜`13`。テキストは `<text>` 要素で書き、パス化しない。
- `<style>` 要素は使わず、すべて属性で指定する。
- 矢印は `<defs>` の `<marker>` を定義して再利用する。**`id` は図ごとに一意にする**。
- `«` `»` `<` `>` `&` をテキストに書くときは、**必ず実体参照でエスケープする**（`&#171;` `&#187;` / `&lt;` `&gt;` / `&amp;`）。生で書くと XML として壊れる。
- テキストの `text-anchor` を明示する（既定に頼って文字が左へはみ出す事故を防ぐ）。
- **実際のホスト名・IP・鍵を図に書かない。**

#### 埋め込み方

- 埋め込み位置は、その図を説明している**章の中**。
- `<svg>` 要素をそのまま本文に書く。前後を空行で挟み、**コードフェンスで囲まない**。
- 根要素の `xmlns="http://www.w3.org/2000/svg"` を必ず残し、**埋め込む側にだけ** `style="max-width:100%;height:auto"` を足す。
- 図の直後に `[図を SVG で開く](img/<ファイル名>.svg)` を 1 行添える。
- 図の直前か直後に、**その図が何を示しているかを 1 行**書く。図だけ置かない。
- **インラインの中身は `.svg` ファイルから機械的にコピーする。** Markdown 側の SVG を手で編集しない。

## 4. 検証と報告

出力前に自己点検する:

- [ ] **上流のコンポーネントがすべて、いずれかの実行単位に配置されているか**（漏れが無いか）
- [ ] 同居／分離の**理由が書かれているか**（「将来のため」で分けていないか）
- [ ] **非同期のインターフェースがすべて、ジョブ基盤の実体に対応づいているか**
- [ ] 冪等キーの判定場所が決まっているか。**重複実行で二重に副作用が起きない**ことを説明できるか
- [ ] **秘密を読める実行単位が最小になっているか**（上流が範囲を限定している場合、それを物理的に実現しているか）
- [ ] **秘密の取り替え方が書かれているか**（取り替えられない設計になっていないか）
- [ ] **出ていける先が列挙され、それ以外を遮断しているか。** 遮断が図で示されているか
- [ ] 公開する必要のないもの（データストア・ジョブ基盤・管理操作）を公開していないか
- [ ] **実行トレースと監査ログの保存先が決まっているか**（上流が未定なら、ここで決めたか）
- [ ] 記録してはいけないもの（個人識別情報・秘密）を落とす場所が決まっているか
- [ ] **本番の鍵と資金に、本番以外の環境から触れない**ことが担保されているか
- [ ] チェーンを使う場合、**環境ごとにネットワークが分かれているか**
- [ ] ライフサイクルの違うもの（頻繁に変わるもの／変えられないもの）を同じデプロイ単位にしていないか
- [ ] **戻せないもの**が明示され、出す前の確認手順があるか
- [ ] **コスト上限を強制する場所が、実行単位の外側にあるか**（アプリ任せになっていないか）
- [ ] **停止手段が具体的に決まっているか。** 誰が・どこで・効くまでの時間。**再デプロイが要る停止手段になっていないか**
- [ ] 外部障害時に何が止まり何が動くかの表があるか。上流が未定なら、**未定と書いたうえで現状の挙動を書いたか**
- [ ] 可用性の目標が未定なのに**過剰な冗長化**をしていないか（根拠のない多重化をしていないか）
- [ ] `infra-runbook.md` に最低限の手順（全体停止・案件停止・再開・秘密の取り替え・デプロイの戻し・取りこぼしからの復旧）がそろっているか
- [ ] 各手順に**誰が・どこで・所要時間・確認方法・戻し方**が書かれているか
- [ ] **上流で解消した未決事項について、上流のファイルも更新したか**（決めたまま放置していないか）
- [ ] 上流 ID を振り直していないか、`INF` / `OPS` / `IQ` / `IR` の ID が重複していないか
      （`grep -oE '\b(INF|OPS|IQ|IR)-[0-9]{3}\b' "$DOCS_DIR"/agent-infra/*.md | sort | uniq -c` で確認）
- [ ] **実際のホスト名・IP・鍵・接続文字列を書いていないか**（プレースホルダになっているか）
- [ ] 出力が Markdown（`.md`）で、見出しレベル・テーブル記法が崩れていないか
- [ ] 保存先が `$DOCS_DIR/agent-infra/` になっているか（リポジトリ内の `docs/` に書いていないか）
- [ ] **SVG がすべて `$DOCS_DIR/agent-infra/img/` に保存されているか**（`agent-infra/` 直下に `.svg` を置いていないか）
- [ ] **作成した SVG がすべて `agent-infra.md` にインラインで埋め込まれているか**（`grep -c '<svg ' agent-infra.md` と `ls img/*.svg | wc -l` が一致するか）
- [ ] 埋め込んだ SVG が `.svg` ファイルと同じ内容か（`style` 属性の追加以外に差分が無いか）
- [ ] **SVG が well-formed か**（`xmllint --noout "$DOCS_DIR"/agent-infra/img/*.svg`。無ければ `python3 -c "import xml.etree.ElementTree as E;E.parse('<path>')"`）
- [ ] 線が交差していないか。棒人間で描いたアクターがすべて人間か

最後にユーザーへ短く報告する:

- 作成・更新したファイル（**フルパスで示す**。設計書 / 運用手順書 / `img/` 配下の図）
- 実行単位の数と、**同居／分離の方針**
- 図の枚数と、分割した場合はその方針
- **本スキルで解消した上流の未決事項**（どれを、どう決めたか）
- **秘密を読める実行単位**（いくつに絞ったか）と、**出ていける先の一覧**（何を遮断したか）
- **停止手段**（誰が・どこで・効くまでの時間。再デプロイ不要か）
- **戻せないもの**の一覧
- 主要な設計判断と、**「仮」のまま残したもの**
- **未決事項の一覧**（`IQ` と、上流に残したもの。ユーザーの回答が必要なものを箇条書きで）

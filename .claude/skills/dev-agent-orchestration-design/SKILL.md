# dev-agent-orchestration-design

アーキテクチャで置いた**エージェントのコンポーネント**を、実際に動かせる制御設計に落とすスキル。

設計するのは次の 6 つ。どれも欠かすと動かない:

1. **役割分担** — どのエージェントが何を担い、何を担わないか
2. **委譲の構造** — 誰が誰を呼ぶか。呼び出しが循環しないか
3. **ツール** — エージェントが呼べる操作と、その副作用
4. **人間の介在点** — どこで人間が判断し、その間どう待つか
5. **ガードレール** — 権限・上限・停止手段。**副作用のあるツールには必ず付ける**
6. **停止条件と再開** — 無限ループ・再試行上限・コスト上限、中断からの再開

ここでは**要件もアーキテクチャも新しく作らない**。エージェントを勝手に増やさない。必要になったら推測で埋めずに未決事項へ上げ、`dev-architecture-design` / `dev-requirements-spec` に差し戻す。

## 1. 入力を読む

| 入力 | 扱い |
|------|------|
| `$DOCS_DIR/architecture/architecture.md` | **一次入力**。エージェントに相当するコンポーネント（CMP）、インターフェース（IF）、横断的関心事、リスク（AR）を引き継ぐ |
| `$DOCS_DIR/architecture/architecture-decisions.md` | エージェントの実現方式に関する ADR。**仮採用のものは、それに依存する設計も仮とする** |
| `$DOCS_DIR/requirements/requirements.md` | ユースケースの基本フロー・例外フロー。**人間の介在点はここから拾う**（要件に無い介在点を足さない） |
| `$DOCS_DIR/database/database-design.md` | エージェントが読み書きするデータ。ツールの入出力を具体化するのに使う（無ければ無いまま進める） |
| `$DOCS_DIR/agent-orchestration/` の既存ファイル | 差分更新のために必ず読む |

- `architecture.md` が無い場合は、**先に `dev-architecture-design` を実行するようユーザーに促す**。それでも進める場合は、エージェントの構成を自分で仮定したことを設計書に明記する。
- **要件 ID（BR / UC / FR / NFR / CON / OUT / Q / R）とアーキテクチャ ID（CMP / IF / ADR / AR / AQ）は絶対に振り直さない。**
- 上流の状態が `仮` / `要確認` のものに依存する設計は、**その部分も「仮」として扱う**。

とくに次を重点的に読む:

1. **エージェントに相当する CMP** — これが `AG` の母集合。ここに無いエージェントを作らない。
2. **横断的関心事の「認可」** — 誰が何をしてよいかが決まっていなければ、ガードレールは設計できない（未決に上げる）。
3. **ユースケースの例外フロー** — エスカレーション先と人間の介在点の根拠。
4. **リスク（AR）** — とくに外部依存・コスト・鍵の扱いは、そのまま停止条件とガードレールの設計材料になる。

## 2. 設計する

### 2-1. エージェントを確定する

アーキテクチャのコンポーネントのうち、**自律的に判断して次の行動を決めるもの**だけをエージェントとして扱う。決められた手順を実行するだけのものはエージェントではない（ワーカー・アダプタとして区別する）。

各エージェントに `AG-001` から採番し、次を定める:

- **目的**（1 文。「〜を管理する」で終わらせない）
- **入力 / 出力**（何を受け取り、何を返すか。型で書く）
- **担わないこと** — これを書かないと責務が際限なく膨らむ
- **対応する CMP**（アーキテクチャのどのコンポーネントか）
- **根拠要件**

**エージェントを増やさない。** 「あると便利そう」で足さない。足す必要があると判断したら、上流へ差し戻す。

### 2-2. ツールを定義する

エージェントが呼べる操作に `TOOL-001` から採番し、**副作用の有無で必ず分類する**。

| 区分 | 意味 | 扱い |
|---|---|---|
| 参照のみ | 状態を変えない | ガードレール不要。ただしコストと件数上限は決める |
| 可逆な変更 | 取り消せる（オフチェーンの下書き等） | 権限を定める |
| **不可逆な変更** | 取り消せない（送金・オンチェーン書き込み・外部への通知・公開） | **必ずガードレールを付ける**（2-5）。人間の承認が要るかを明示する |

各ツールに定める項目:

- 名前・目的・**呼べるエージェント**（複数可）
- 入力 / 出力のスキーマ（JSON Schema か、それに準じた表）
- 副作用の区分、**冪等か**（同じ入力で 2 回呼んだらどうなるか）
- 失敗時の挙動（再試行してよいか、何回まで）
- 根拠要件

**エージェントに渡すツールは最小限にする。** 「念のため」で権限の広いツールを渡さない。

### 2-3. 委譲の構造を決める

- **オーケストレーションの型を選び、理由を書く。**
  - 中央集権（1 つのオーケストレータが全部を指揮）
  - 階層（親エージェントが子に委譲し、子はさらに委譲する）
  - 分散（エージェント同士が直接やり取りする）
  - 要件の性質（監査可能性・停止のしやすさ・並列性）から選ぶ。一般論で選ばない。
- **呼び出しの向きを循環させない。** 循環したら役割の切り方が間違っている。切り直す。
- エージェント間で受け渡す情報を決める。**丸ごとの会話履歴を渡さない**（コストと事故の元）。何を渡すかを型で書く。

### 2-4. 人間の介在点を決める

`HIL-001` から採番し、**要件に根拠があるものだけ**を置く。

各介在点に定める項目:

- **どの手順の直前・直後か**（UC-ID と手順番号で特定する）
- 誰が（アクター）、何を判断するか
- **同期か非同期か。** 非同期なら、待っている間の状態をどこに持ち、いつタイムアウトするか
- 人間が応答しなかった場合の既定動作（**「待ち続ける」は設計ではない**）
- 根拠要件

**要件に無い介在点を足さない。** 逆に、要件が人間の判断を求めているのに介在点が無い箇所があれば、それは設計漏れとして明記する。

### 2-5. ガードレールを決める

`GRD-001` から採番する。**不可逆なツールすべてに、最低 1 つのガードレールが対応していること。**

最低限、次を検討する:

| 種類 | 問い |
|---|---|
| 権限 | そのエージェントは、その操作をしてよいと誰が認めたか |
| 上限 | 金額・件数・回数・時間の上限はいくつか。**「無制限」は上限ではない** |
| 承認 | 人間の承認を必須にする操作はどれか（2-4 と対応させる） |
| 停止 | 暴走したとき、誰がどうやって止めるか。**停止の手段が無い設計を出さない** |
| 失効 | 権限はいつ切れるか。案件終了後も残らないか |
| 検証 | エージェントの出力を、副作用を起こす前にどう検証するか |

要件に記述が無いものは、**推測で決めずに未決事項へ上げる**。ただし「停止手段が無い」ことは、未決ではなく**リスク**として必ず明記する。

### 2-6. 非決定性への対処を決める

LLM は同じ入力でも同じ出力を返さない。これを前提に次を決める:

- **出力の構造化** — 自由文ではなく、スキーマの決まった構造で受け取る。スキーマは 2-2 のツール定義と揃える。
- **検証** — 受け取った出力を、副作用を起こす**前**に検証する。何を検証するか（必須項目・値域・参照先の実在・合計額が予算内か 等）を書く。
- **検証に失敗したときの再試行** — 何回まで、どう変えて再試行するか。**上限に達したらどうするか**（エスカレーション先）。
- **決定性が要る箇所** — 同じ入力から必ず同じ結果が要る処理（識別子の生成、金額の計算）は、**エージェントにやらせない**。どこで通常のコードに落とすかを明記する。

### 2-7. 状態・再開・冪等性

- エージェントの実行は長時間にわたり、人間待ちで中断する。**どこまで進んだかをどこに持つか**を決める（データ設計と整合させる）。
- 中断から再開したとき、**やり直してよい手順と、やり直してはいけない手順**を分ける。
- 不可逆なツールの呼び出しは**冪等キー**を持たせる。同じ手順を 2 回実行しても副作用が 1 回で済むようにする。

### 2-8. 停止条件とコスト

**すべてのエージェントに停止条件を定める。** 1 つでも欠けたら設計として不完全。

| 条件 | 決めること |
|---|---|
| 反復上限 | 1 つの目的あたり、最大何回まで思考・ツール呼び出しを繰り返すか |
| 時間上限 | 1 実行あたりの上限時間 |
| コスト上限 | 1 実行・1 案件あたりのトークン／費用の上限。**誰が負担するかが未定なら、上限の根拠も未定**として明記する |
| 打ち切り時の挙動 | 上限に達したら何をするか（人間へエスカレーション／安全に中断／巻き戻し） |

### 2-9. 観測とエスカレーション

- **何を記録するか** — 入力・出力・ツール呼び出し・判断の根拠・コスト。上流に監査ログの要件があれば、それと整合させる。
- **記録してはいけないもの** — 個人識別情報・秘密鍵・生の認証情報。上流のプライバシー要件に従う。
- **エスカレーション先** — エージェントが判断できないとき、誰に渡すか。`HIL` と対応づける。

### 2-10. 定義データ／プロンプトの設計方針

エージェントの振る舞いが**データとして外から与えられる**設計（利用者が作ったエージェント定義を読み込む等）の場合は、次も決める:

- 定義データのスキーマ（上流のデータ設計と同一にする。二重定義しない）
- **定義データで変えてよい範囲と、変えさせない範囲**（ツールの追加・上限の緩和は変えさせない）
- 悪意ある定義への耐性（指示の上書き、権限の逸脱）をどう防ぐか。**防げないなら、防げないと書く**

### 2-11. ID の採番

| 対象 | ID | 備考 |
|---|---|---|
| エージェント | `AG-001` | アーキテクチャの CMP に必ず対応づける |
| ツール | `TOOL-001` | 副作用の区分を必ず持たせる |
| 人間の介在点 | `HIL-001` | UC の手順に対応づける |
| ガードレール | `GRD-001` | 不可逆なツールに最低 1 つ |
| 設計上の未決事項 | `OQ-001` | 上流の `Q` / `AQ` / `DQ` とは別系列 |
| 設計上のリスク | `OR-001` | 上流の `R` / `AR` とは別系列 |

- **上流の欠落**を見つけた場合は `OQ` ではなく、**上流に `Q-nnn` / `AQ-nnn` を追加して差し戻す**（該当ファイルと変更履歴の両方を更新する）。`OQ` は「上流は決まっているが、オーケストレーション設計の選択が残っている」ものに使う。
- 既存の設計書がある場合は必ず先に読み、**既存の ID を再利用して振り直さない**（廃止するものは行を残して「廃止」と記す）。

### 3-2. `$DOCS_DIR/agent-orchestration/agent-definitions.md`（定義カタログ）

1 エージェント 1 節。**実装者がこれだけ読んで着手できる粒度**にする。

```markdown
# エージェント定義カタログ

> 最終更新: YYYY-MM-DD

## AG-001 <名称>

- **対応CMP**: CMP-00x
- **目的**: 1 文
- **担わないこと**: 箇条書き
- **入力**: 型と意味
- **出力**: 型と意味（```json でスキーマ）
- **使えるツール**: TOOL-00x（副作用の区分を併記）
- **呼び出せるエージェント**: AG-00x（無ければ「無し」）
- **人間の介在点**: HIL-00x
- **ガードレール**: GRD-00x
- **停止条件**: 反復上限 / 時間上限 / コスト上限
- **失敗時の挙動**: 再試行回数と、上限到達時のエスカレーション先
- **プロンプト方針**: 何を指示に含め、何を含めないか（**プロンプト本文は書かない。方針だけ書く**）
- **根拠要件**: FR-00x, NFR-00x
```

- **プロンプトの本文をこの設計書に書かない。** 実装で変わるものを設計書に固定すると、必ず食い違う。方針（何を入れ、何を入れないか）だけを書く。

### 3-3. 図（SVG）

**構造の図は必ず SVG で作成し、`$DOCS_DIR/agent-orchestration/img/` に保存したうえで、その中身を `agent-orchestration.md` にインラインで埋め込む。**

#### 作る図

| ファイル名 | 図 | 何を示すか | 作らなくてよい場合 |
|---|---|---|---|
| `01-agent-topology.svg` | 編成図 | エージェント・人間・外部システムと、委譲の向き | **必ず作る** |
| `02-tool-matrix.svg` | ツール権限図 | エージェント × ツール の対応と、副作用・ガードレールの別 | **必ず作る** |
| `03-human-in-the-loop.svg` | 介在点図 | 人間が判断する箇所と、待機・タイムアウトの流れ | 介在点が 2 つ以下 |
| `04-<主題>.svg` | 補助図 | 上記で表せない構造 | 上記で足りる場合 |

図ありきで作らない。**表で足りるなら作らない。** ただし `01` と `02` は必ず作る。

#### 記法

| 要素 | 記法 |
|---|---|
| エージェント | 角丸の矩形 + `«agent»` のステレオタイプ。中に `AG-001` と名称 |
| ツール | 角丸の矩形 + `«tool»`。**副作用の区分で塗りを変える**（参照のみ／可逆／不可逆） |
| 人間のアクター | 棒人間 + 直下に名称 |
| 外部システム | 角丸の矩形 + `«system»` |
| 委譲・呼び出し | 実線 + 矢印。**向きを必ず付ける**。ラベルに何を渡すかを書く |
| 非同期 | 破線 + 矢印 |
| 人間の介在点 | 実線の菱形か、`HIL-001` を添えた印。介在する位置に置く |
| ガードレール | 対象を囲む破線の矩形 + `GRD-001` のラベル |
| 凡例 | 図の下部に必ず置く |

- **人間でないものを棒人間で描かない。** エージェント・ツール・外部システムは利用者ではないので、棒人間で描くと読み違えられる。箱 + ステレオタイプで描く。
  - 判断基準: **その相手は画面を操作したり意思決定をしたりする人間か？** いいえなら箱にする。
- **不可逆なツールは一目で分かるようにする。** 色だけに頼らず、`«tool: 不可逆»` のようにステレオタイプにも書く。
- 設計書の表と **ID・名称を完全に一致**させる。図だけの略称を作らない。

#### レイアウト規則

- **委譲の向きを揃える**（上から下、または左から右）。逆流する線があれば、役割の切り方を見直す。
- 人間のアクターは外側（上端か左端）、ツールと外部システムはその反対側にまとめる。
- **線を交差させない。** 交差しそうならノードの並び順を入れ替える。
- ノードが 20 を超えて読めなくなる場合は、**上位だけを描くか領域ごとに分割**する。

#### SVG の書き方（必須ルール）

- ルートは `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 W H" width="W" height="H">`。`viewBox` を必ず付ける。
- **ダーク/ライト両対応**: 背景に `<rect fill="#ffffff">` を敷き、線と文字は濃色（`#1f2937`）で描く。`currentColor` や CSS 変数に頼らない。
- フォントは `font-family="'Noto Sans JP','Hiragino Sans','Yu Gothic',sans-serif"`、本文 `font-size="12"`〜`13`。テキストは `<text>` 要素で書き、パス化しない。
- `<style>` 要素は使わず、すべて属性で指定する。
- 矢印は `<defs>` の `<marker>` を定義して再利用する。**`id` は図ごとに一意にする**（同じ Markdown に複数の SVG を埋めると id が衝突するため）。
- `«` `»` や `<` `>` をテキストに書くときは、**必ず実体参照でエスケープする**（`&#171;` `&#187;` / `&lt;` `&gt;`）。生で書くと XML として壊れる。
- 手書きで組み立てる。作図ツールの巨大な出力を貼り付けない。

#### 埋め込み方

- 埋め込み位置は、その図を説明している**章の中**。
- `<svg>` 要素をそのまま本文に書く。前後を空行で挟み、**コードフェンスで囲まない**。
- 根要素の `xmlns="http://www.w3.org/2000/svg"` を必ず残し、**埋め込む側にだけ** `style="max-width:100%;height:auto"` を足す。
- 図の直後に `[図を SVG で開く](img/<ファイル名>.svg)` を 1 行添える（GitHub はインライン SVG を表示しないため）。
- 図の直前か直後に、**その図が何を示しているかを 1 行**書く。図だけ置かない。
- **インラインの中身は `.svg` ファイルから機械的にコピーする。** Markdown 側の SVG を手で編集しない。

## 4. 検証と報告

出力前に自己点検する:

- [ ] **すべてのエージェントがアーキテクチャの CMP に対応づいているか**（上流に無いエージェントを作っていないか）
- [ ] すべてのエージェントに「担わないこと」が書かれているか
- [ ] **すべてのツールに副作用の区分と冪等性が書かれているか**
- [ ] **不可逆なツールすべてに、最低 1 つのガードレールが対応しているか**（対応表で確認する）
- [ ] ガードレールの上限が**数値で**書かれているか（「適切に制限する」で済ませていないか）
- [ ] **暴走時の停止手段が書かれているか**（無いなら、無いことをリスクとして明記したか）
- [ ] **すべてのエージェントに停止条件（反復・時間・コスト）が定義されているか**。1 つでも欠けていないか
- [ ] 人間の介在点が**要件に根拠を持つか**。要件が人間の判断を求めているのに介在点が無い箇所を見落としていないか
- [ ] 各介在点に**タイムアウト時の既定動作**が書かれているか（「待ち続ける」になっていないか）
- [ ] 非決定性への対処（出力の検証・再試行上限・エスカレーション先）が書かれているか
- [ ] **決定性が要る処理をエージェントにやらせていないか**（識別子の生成・金額の計算など）
- [ ] 委譲の呼び出しに**循環が無いか**。参照先の AG-ID が実在するか
- [ ] 中断からの再開時に、やり直してはいけない手順が識別されているか。不可逆な操作に冪等キーがあるか
- [ ] 記録してはいけない項目（個人識別情報・秘密鍵）を記録対象に入れていないか
- [ ] 定義データでツールの追加や上限の緩和ができてしまわないか
- [ ] `agent-definitions.md` の全エージェントが `agent-orchestration.md` の一覧と一致しているか（過不足が無いか）
- [ ] 上流 ID を振り直していないか、`AG` / `TOOL` / `HIL` / `GRD` / `OQ` / `OR` の ID が重複していないか
      （`grep -oE '\b(AG|TOOL|HIL|GRD|OQ|OR)-[0-9]{3}\b' "$DOCS_DIR"/agent-orchestration/*.md | sort | uniq -c` で確認）
- [ ] 出力が Markdown（`.md`）で、見出しレベル・テーブル記法が崩れていないか
- [ ] 保存先が `$DOCS_DIR/agent-orchestration/` になっているか（リポジトリ内の `docs/` に書いていないか）
- [ ] **SVG がすべて `$DOCS_DIR/agent-orchestration/img/` に保存されているか**（`agent-orchestration/` 直下に `.svg` を置いていないか）
- [ ] **作成した SVG がすべて `agent-orchestration.md` にインラインで埋め込まれているか**（`grep -c '<svg ' agent-orchestration.md` と `ls img/*.svg | wc -l` が一致するか）
- [ ] 埋め込んだ SVG が `.svg` ファイルと同じ内容か（`style` 属性の追加以外に差分が無いか）

- [ ] **棒人間で描いたアクターがすべて人間か**（エージェント・ツール・外部システムを棒人間にしていないか）
- [ ] 図の中の ID・名称が設計書の表と一致しているか。線が交差していないか
- [ ] Mermaid の構文が正しいか（`npx` が使えるなら `npx -y @mermaid-js/mermaid-cli -i <入力>.md -o <スクラッチパッド>/check.md` で確かめる。使えなければ目視確認し、未検証であることを報告に書く）
- [ ] **プロンプトの本文を設計書に書いていないか**（方針だけになっているか）

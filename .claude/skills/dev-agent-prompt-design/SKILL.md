# dev-agent-prompt-design

コンテキスト設計が決めた**構造の中に入れる「本文」**を設計するスキル。

上流との分担は次のとおり。**ここを混ぜない。**

| 工程 | 決めるもの |
|---|---|
| `dev-agent-orchestration-design` | 誰が何を担い、どのツールを持ち、どこで人間が入るか |
| `dev-agent-context-design` | コンテキストを何の塊に分け、どの順に、何トークンまで入れるか |
| **本スキル** | **その塊に入る文章そのもの**。役割と制約の指示、出力形式の指示、再試行の指示、**委譲プロンプト** |

**マルチエージェントの場合は、オーケストレータからサブエージェントへ渡す委譲プロンプトも必ず設計する。** サブエージェントは自分で状況を調べに行けないため、**委譲プロンプトが唯一の入力**になる。ここを設計しないとサブエージェントは動かない。

ここでは**エージェントもツールもコンテキストブロックも新しく作らない**。必要になったら推測で埋めずに未決事項へ上げ、上流に差し戻す。

## 0. 作業ディレクトリ

**読み取り先・保存先はどちらも次のディレクトリ**（リポジトリ内の `docs/` ではない）:

```bash
DOCS_DIR=/mnt/c/second-brain/ethglobal_hackathon/docs
```

- 入力資料: `$DOCS_DIR/` 配下（とくに `$DOCS_DIR/agent-context/`、`$DOCS_DIR/agent-orchestration/`）
- 出力先: `$DOCS_DIR/agent-prompt/`（Markdown）／`$DOCS_DIR/agent-prompt/img/`（**図の SVG はすべてここに置く**）
- このディレクトリは **Obsidian の vault**（Windows 側 `C:\second-brain`）を WSL からマウントしたもの。以下に注意する:
  - `.obsidian/` 配下と `*:Zone.Identifier` は入力から除外する。
  - 改行は LF、文字コードは UTF-8 で書く。
  - Obsidian で開けるよう、**見出し・テーブル・チェックリスト・コードブロックは標準の Markdown 記法**に収める。
- **解析対象から除外するファイル**（ユーザー指示 2026-09-25。読み込まない・出典にも使わない）:
  - `01-アーキテクチャ図.svg`
  - `02-アーキテクチャ図-WorldMiniApp案.svg`
  - `ETH_Globalユースケース.pdf`
  ユーザーが明示的に「この資料も見て」と指定した場合にだけ読む。その場合は使ったことを報告する。
- ディレクトリが存在しない／アクセスできない場合は、勝手に別の場所へ書かず、ユーザーにパスを確認する。
- ユーザーが `docs/xxx.md` のような相対パスを渡した場合は、**`$DOCS_DIR` 起点として解決する**。

## 1. 入力を読む

| 入力 | 扱い |
|------|------|
| `$DOCS_DIR/agent-context/context-templates.md` | **一次入力**。各エージェントが使うブロック・並び順・**トークン上限**。本文はこの上限に収める |
| `$DOCS_DIR/agent-context/agent-context.md` | ブロックの信頼区分・ガード・入れてはいけない情報。**本文に埋め込んでよいもの／いけないものはここで決まっている** |
| `$DOCS_DIR/agent-orchestration/agent-definitions.md` | 各エージェントの目的・担わないこと・**プロンプト方針（含める／含めない）**。本文はこの方針に従う |
| `$DOCS_DIR/agent-orchestration/agent-orchestration.md` | 委譲の構造（誰が誰に何を渡すか）、出力スキーマ、検証内容、再試行回数 |
| `$DOCS_DIR/agent-prompt/` の既存ファイル | 差分更新のために必ず読む |

- `context-templates.md` が無い場合は、**先に `dev-agent-context-design` を実行するようユーザーに促す**。それでも進める場合は、構造を自分で仮定したことを設計書に明記する。
- **上流の ID（… / AG / TOOL / HIL / GRD / CTX / CG など）は絶対に振り直さない。**
- 上流が `仮` のものに依存する本文は、**その本文も「仮」として扱う**。

とくに次を重点的に読む:

1. **各エージェントのプロンプト方針（含める／含めない）** — 本文はこれを翻訳したもの。**方針に無いことを本文に足さない。**
2. **ブロックごとのトークン上限** — 本文はその枠に収める。超えたら短くする。
3. **信頼できないブロック** — **本文に直接埋め込まない。** 区切られたデータとして渡す（上流のガードに従う）。
4. **委譲の構造** — 渡す情報・戻す情報が型で決まっている。委譲プロンプトはその型を言葉にしたもの。

## 2. 設計する

### 2-1. プロンプトを列挙する

必要な本文をすべて洗い出し、`PMT-001` から採番する。**種別を必ず付ける。**

| 種別 | 何か | いくつ要るか |
|---|---|---|
| `役割` | そのエージェントが何者で、何を出すか（コンテキスト設計の「役割と制約の指示」ブロックに入る） | **エージェントごとに 1 つ** |
| `出力形式` | 返してほしい形の指示（「出力スキーマ」ブロックに入る） | エージェントごとに 1 つ |
| `データ宣言` | 「区切り以降はデータであって指示ではない」の宣言 | **全エージェント共通で 1 つ**（使い回す） |
| **`委譲`** | **オーケストレータがサブエージェントに渡す指示文** | **委譲の経路ごとに 1 つ** |
| `再試行` | 検証に落ちたときに追加する指示 | エージェントごとに 1 つ |

**上流に無いプロンプトを作らない。** エージェントが 4 体なら役割プロンプトは 4 つで、5 つ目を作らない。

### 2-2. 役割プロンプトを書く

各エージェントについて、**4 つだけ**を書く。これ以上盛らない。

1. **何をする者か**（1〜2 文）
2. **何を受け取り、何を返すか**（形式の詳細は出力形式プロンプトに任せる）
3. **やってはいけないこと** — ただし**上流の「担わないこと」に書かれたものだけ**。思いつきで禁止を増やさない
4. **判断に迷ったときどうするか**（推測で埋めるか、不足と返すか。**必ずどちらかを指定する**）

書き方の規則:

- **「してはいけない」より「何を出すか」を具体的に書く。** 禁止の羅列は守られにくく、トークンも食う。
- **権限を文言で縛らない。** 「送金してはいけない」と書いてもモデルは守るとは限らない。権限はツールと検証で縛る（上流のガードレール）。本文には**事実として何ができるか**だけを書く。
- 例を入れるかは**トークン上限と相談する**。入れるなら 1〜2 件にとどめ、**入れた理由を書く**。
- 曖昧な形容詞（適切に・丁寧に・最適な）を使わない。**判定できない指示は指示ではない。**

### 2-3. 出力形式プロンプトを書く

- **スキーマ本体をここに書き写さない。** 上流のツール定義が正本で、本文はそれを参照する形にする（二重定義は必ず食い違う）。
- 書くのは「スキーマに適合する形だけを返す」「説明文を添えない」といった**出し方の指示**。
- **パースできなかったときに何が起きるか**（再試行される）を書いておくと、モデルが形式を守りやすい。

### 2-4. 委譲プロンプトを書く（マルチエージェントの場合は必須）

オーケストレータがサブエージェントを呼ぶとき、**サブエージェントが見る入力はこの委譲プロンプトだけ**である。サブエージェントは自分で DB を見に行けないし、前の経緯も知らない。

委譲プロンプトに**必ず含める 5 つ**:

1. **今回の目的**（1 文。「タスクに分解せよ」など）
2. **必要なデータ**（区切って渡す。**どれが信頼できない入力かを、渡す側が区別して配置する**）
3. **返してほしい形**（出力形式プロンプトへの参照でよい）
4. **守るべき制約**（予算内に収める、結論を書かない、など。**上流の検証内容と一致させる**）
5. **判断できないときの返し方**（空で返す・不足を返す。**「頑張って推測する」にしない**）

委譲プロンプトに**含めてはいけない 4 つ**:

- **会話履歴**（オーケストレータとのやり取りの経緯）
- **他の委譲で得た中間出力**（必要な分だけを 2 の「必要なデータ」として渡す）
- **オーケストレータの内部状態**（どの手順にいるか、何回目の再試行か等。サブエージェントの判断に不要）
- **他の案件・他の利用者のデータ**

**重要な区別** — 委譲プロンプトの**指示部分は信頼できる**（自分たちが書いた）が、**その中で渡すデータは信頼できないことがある**（利用者の入力や第三者の文字列）。両者を同じ塊に混ぜない。**指示を先に、データを区切って後に**置く。

### 2-5. 再試行プロンプトを書く

- **何が違反したかだけ**を書く。**前回の出力を貼り直さない**（上流のガードで禁じられている場合はとくに）。
- 「もう一度やり直せ」ではなく、**どう直すか**を具体的に書く（「合計が予算を 12,000 超えている。金額を下げて再提出せよ」）。
- 再試行の回数は上流の値に従う。**プロンプトで回数を制御しない。**

### 2-6. トークン量を実測する

- 各プロンプトの**トークン数を数えて書く**。コンテキスト設計のブロック上限に収まるかを確かめる。
- 収まらなければ**本文を短くする**。上限のほうを勝手に広げない（広げるなら上流へ差し戻す）。
- 日本語は英語よりトークンを食う。**言語を選べるなら、どちらで書くかを理由とともに決める。**

### 2-7. 版管理と変更の扱い

- **すべてのプロンプトに版を付ける**（`PMT-001 v1` のように）。プロンプトは必ず変わる。
- 版ごとに「何を変えたか」「なぜ変えたか」「評価結果がどう変わったか」を記録する。
- **本文の正本はこのカタログに置く。** 実装がここを参照する形にし、コードとドキュメントに同じ文言を二重に持たない（必ず食い違う）。

### 2-8. 評価と紐づける

- **上流（コンテキスト設計）の評価入力をそのまま使う。** ここで別の評価セットを作らない。
- プロンプトを変えたら、**同じ入力で再評価して合否を記録する**。
- 合格基準は上流と同じ（**スキーマ適合・検証通過・権限の逸脱なし**）。**文章の良し悪しを基準にしない。**

### 2-9. 入れてはいけないもの

上流の「入れてはいけない情報」に加え、**本文に特有のもの**を確認する:

- 秘密鍵・API キー・接続情報（本文に書かない。当然だが確認する）
- 個人識別情報（例として架空の氏名を書く場合も、実在しそうなものを避ける）
- **上限値や閾値のうち、変わりやすいもの**（本文に埋め込むと変更時に本文ごと差し替えになる。**構造化された値として渡す**）
- 特定モデルの癖に依存した言い回し（モデルを変えると壊れる。**依存する場合はそう明記する**）

### 2-10. ID の採番

| 対象 | ID | 備考 |
|---|---|---|
| プロンプト | `PMT-001` | 種別（役割 / 出力形式 / データ宣言 / 委譲 / 再試行）と版を必ず持たせる |
| 設計上の未決事項 | `PQ-001` | 上流の `Q` / `AQ` / `OQ` / `CQ` とは別系列 |
| 設計上のリスク | `PR-001` | 上流の `R` / `AR` / `OR` / `CR` とは別系列 |

- **上流の欠落**を見つけた場合は `PQ` ではなく、**上流に差し戻す**（該当ファイルと変更履歴の両方を更新する）。
- 既存の設計書がある場合は必ず先に読み、**既存の ID と版を振り直さない**（廃止するものは行を残して「廃止」と記す）。

## 3. 出力する

**設計書とカタログは必ず Markdown（`.md`）で、構造の図は必ず SVG（`.svg`）で作成する。**

出力先は **`$DOCS_DIR/agent-prompt/`**（リポジトリ内の `docs/` には書かない）。**SVG は `img/` サブディレクトリに置く。** 無ければ作成する:

```bash
mkdir -p "$DOCS_DIR/agent-prompt/img"
```

出力は次の 2 点 + 図:

| ファイル | 内容 |
|---|---|
| `agent-prompt.md` | プロンプト設計書（方針・一覧・トークン量・版管理・評価。図をインライン埋め込み） |
| `prompt-library.md` | **プロンプト本文のカタログ（本文の正本）** |
| `img/*.svg` | 対応図・委譲プロンプトの構造図（3-3 参照） |

既存ファイルがあれば内容を読み、上書きではなく **差分更新** とし、変更点を「変更履歴」に追記する。

Markdown の書き方ルール:

- 見出しは `#` → `##` → `###` の順に、レベルを飛ばさずに使う。
- 一覧は **GFM のテーブル**で書く。セル内改行は `<br>`、セル内の `|` は `\|` にエスケープする。
- **プロンプトの本文は ```` ```text ```` のコードブロックに入れる。** 地の文に混ぜない（どこからどこまでが本文か分からなくなる）。
- 差し込む値は `{{project_id}}` のような**プレースホルダ**で書き、**実データを本文に埋め込まない**。
- 構造の図は SVG。処理の流れが要る場合は Mermaid（```` ```mermaid ````）。
- 画像は `agent-prompt/img/` 配下の自前ファイルのみ参照する（相対パスは `img/<ファイル名>.svg`）。

### 3-3. 図（SVG）

**構造の図は必ず SVG で作成し、`$DOCS_DIR/agent-prompt/img/` に保存したうえで、その中身を `agent-prompt.md` にインラインで埋め込む。**

#### 作る図

| ファイル名 | 図 | 何を示すか | 作らなくてよい場合 |
|---|---|---|---|
| `01-prompt-map.svg` | 対応図 | どのプロンプトが、どのエージェントの・どのコンテキストブロックに入るか | **必ず作る** |
| `02-delegation-prompt.svg` | 委譲プロンプトの構造図 | オーケストレータ → サブエージェントで、指示部分とデータ部分をどう分けて渡すか | **委譲が無い（単一エージェント）場合のみ省略可** |
| `03-<主題>.svg` | 補助図 | 上記で表せない構造 | 上記で足りる場合 |

図ありきで作らない。**表で足りるなら作らない。** ただし `01` は必ず作る。

#### 記法

| 要素 | 記法 |
|---|---|
| プロンプト | 角丸の矩形。中に `PMT-001`・種別・版 |
| コンテキストブロック | 角丸の矩形 + `«CTX-00x»`。**上流の ID と名称をそのまま使う** |
| エージェント | 角丸の矩形 + `«agent»` |
| **指示部分 / データ部分** | 委譲プロンプトの図では**塗りと枠線で区別し、`«指示»` / `«データ: 信頼できない»` のステレオタイプも付ける**（色だけに頼らない） |
| 対応 | 実線 + 矢印。「このプロンプトがこのブロックに入る」向き |
| 人間のアクター | 棒人間 + 直下に名称 |
| 凡例 | 図の下部に必ず置く |

- **人間でないものを棒人間で描かない。** 判断基準は「その相手は画面を操作したり意思決定をしたりする人間か？」。いいえなら箱にする。
- 図の中の ID・名称・トークン数は**設計書の表と完全に一致**させる。概数にしない。

#### レイアウト規則

- 対応図は**左にプロンプト、右にブロック（またはエージェント）**を置き、流れを左から右に揃える。
- 委譲プロンプトの図は**上にオーケストレータ、下にサブエージェント**を置き、間に渡す中身を並べる。
- **線を交差させない。** 交差しそうならノードの並び順を入れ替える。
- プロンプトが 15 を超える場合はエージェント別に分割する。

#### SVG の書き方（必須ルール）

- ルートは `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 W H" width="W" height="H">`。`viewBox` を必ず付ける。
- **ダーク/ライト両対応**: 背景に `<rect fill="#ffffff">` を敷き、線と文字は濃色（`#1f2937`）で描く。`currentColor` や CSS 変数に頼らない。
- フォントは `font-family="'Noto Sans JP','Hiragino Sans','Yu Gothic',sans-serif"`、本文 `font-size="12"`〜`13`。テキストは `<text>` 要素で書き、パス化しない。
- `<style>` 要素は使わず、すべて属性で指定する。
- 矢印は `<defs>` の `<marker>` を定義して再利用する。**`id` は図ごとに一意にする**。
- `«` `»` や `<` `>` `{` `}` をテキストに書くときは、**山括弧とアンパサンドを必ず実体参照でエスケープする**（`&#171;` `&#187;` / `&lt;` `&gt;` / `&amp;`）。生で書くと XML として壊れる。
- テキストの `text-anchor` を明示する（既定に頼って文字が左へはみ出す事故を防ぐ）。
- **プロンプトの本文を図に書かない。** 図に載せるのは ID・種別・版・対応関係だけ。

#### 埋め込み方

- 埋め込み位置は、その図を説明している**章の中**。
- `<svg>` 要素をそのまま本文に書く。前後を空行で挟み、**コードフェンスで囲まない**。
- 根要素の `xmlns="http://www.w3.org/2000/svg"` を必ず残し、**埋め込む側にだけ** `style="max-width:100%;height:auto"` を足す。
- 図の直後に `[図を SVG で開く](img/<ファイル名>.svg)` を 1 行添える。
- 図の直前か直後に、**その図が何を示しているかを 1 行**書く。図だけ置かない。
- **インラインの中身は `.svg` ファイルから機械的にコピーする。** Markdown 側の SVG を手で編集しない。

## 4. 検証と報告

出力前に自己点検する:

- [ ] **すべてのエージェントに役割プロンプトと出力形式プロンプトがあるか**（過不足が無いか）
- [ ] **すべての委譲経路に委譲プロンプトがあるか**（マルチエージェントで 1 本でも欠けていないか）
- [ ] 各委譲プロンプトに、**含める 5 つ**（目的・データ・返す形・制約・判断できないときの返し方）がそろっているか
- [ ] 各委譲プロンプトが、**含めてはいけない 4 つ**（会話履歴・他の中間出力・内部状態・他案件）を含んでいないか
- [ ] **指示部分とデータ部分が分かれているか。** 信頼できない入力を本文に直接埋め込んでいないか
- [ ] **権限を文言で縛っていないか**（ツールと検証で縛る旨が書かれているか）
- [ ] 出力スキーマを本文に書き写していないか（上流のツール定義を参照する形か）
- [ ] 曖昧な形容詞（適切に・丁寧に・最適な）が残っていないか。**判定できない指示になっていないか**
- [ ] 「判断に迷ったときどうするか」が**全プロンプトに書かれているか**
- [ ] **すべてのプロンプトにトークン数が実測値で書かれ、ブロックの上限に収まっているか**。超えたものを上限のほうを広げて解決していないか
- [ ] すべてのプロンプトに**版**が付いているか。古い版を消していないか
- [ ] プレースホルダの出どころがすべて書かれているか。**実データを本文に埋め込んでいないか**
- [ ] 秘密情報・個人識別情報・変わりやすい閾値を本文に書いていないか
- [ ] 評価が**上流の評価入力**と紐づいているか。合格基準が「スキーマ適合・検証通過・権限の逸脱なし」になっているか
- [ ] `prompt-library.md` の全プロンプトが `agent-prompt.md` の一覧と一致しているか
- [ ] 上流 ID を振り直していないか、`PMT` / `PQ` / `PR` の ID が重複していないか
      （`grep -oE '\b(PMT|PQ|PR)-[0-9]{3}\b' "$DOCS_DIR"/agent-prompt/*.md | sort | uniq -c` で確認）
- [ ] 出力が Markdown（`.md`）で、見出しレベル・テーブル記法が崩れていないか
- [ ] **本文が ```text のコードブロックに入っているか**（地の文に混ざっていないか）
- [ ] 保存先が `$DOCS_DIR/agent-prompt/` になっているか（リポジトリ内の `docs/` に書いていないか）
- [ ] **SVG がすべて `$DOCS_DIR/agent-prompt/img/` に保存されているか**（`agent-prompt/` 直下に `.svg` を置いていないか）
- [ ] **作成した SVG がすべて `agent-prompt.md` にインラインで埋め込まれているか**（`grep -c '<svg ' agent-prompt.md` と `ls img/*.svg | wc -l` が一致するか）
- [ ] 埋め込んだ SVG が `.svg` ファイルと同じ内容か（`style` 属性の追加以外に差分が無いか）
- [ ] **SVG が well-formed か**（`xmllint --noout "$DOCS_DIR"/agent-prompt/img/*.svg`。無ければ `python3 -c "import xml.etree.ElementTree as E;E.parse('<path>')"`）
- [ ] **図にプロンプト本文を書いていないか**。図の ID・トークン数が設計書と一致しているか
- [ ] 線が交差していないか。棒人間で描いたアクターがすべて人間か

最後にユーザーへ短く報告する:

- 作成・更新したファイル（**フルパスで示す**。設計書 / 本文カタログ / `img/` 配下の図）
- プロンプト数（種別ごと）と、**委譲プロンプトが全経路をカバーしているか**
- 図の枚数と、分割した場合はその方針
- **トークン量の実測結果**（各プロンプトと、ブロック上限に収まっているか。収まらなかったものはどう短くしたか）
- **意図的に書かなかったこと**（権限の禁止をプロンプトに書いていない、等）とその理由
- 主要な設計判断と、**「仮」のまま残したもの**
- **未決事項の一覧**（`PQ` と、上流へ差し戻したもの。ユーザーの回答が必要なものを箇条書きで）

## 5. 後続への引き渡し

設計が固まったら、ユーザーに次を提案する（実行は求められたときだけ）:

- **`dev-agent-infra-design` スキル** — エージェントを実際に動かす基盤（実行単位・非同期ジョブ・ネットワーク境界・秘密情報・停止手段）を決める。**プロンプトのデプロイ単位もここで決まる**

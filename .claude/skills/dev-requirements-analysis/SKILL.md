# dev-requirements-analysis

資料を読み、**要求を分解して ID を振り、解析結果を 1 枚のメモにまとめる**スキル。
要件定義書は書かない。出力した `analysis.md` を `dev-requirements-spec` が受け取って清書する。

## 0. 作業ディレクトリ

**読み取り先・保存先はどちらも次のディレクトリ**（リポジトリ内の `docs/` ではない）:

```bash
DOCS_DIR=/mnt/c/second-brain/ethglobal_hackathon/docs
```

- 入力資料: `$DOCS_DIR/` 配下
- 出力先: `$DOCS_DIR/requirements/`（メモ本体）／`$DOCS_DIR/requirements/img/`（図の SVG）
- このディレクトリは **Obsidian の vault**（Windows 側 `C:\second-brain`）を WSL からマウントしたもの。以下に注意する:
  - `.obsidian/` 配下と `*:Zone.Identifier` は入力から除外する。
  - 改行は LF、文字コードは UTF-8 で書く。
  - Obsidian で開けるよう、**見出し・テーブル・チェックリストは標準の Markdown 記法**に収める。
- **解析対象から除外するファイル**（ユーザー指示 2026-09-25。読み込まない・出典にも使わない）:
  - `01-アーキテクチャ図.svg`
  - `02-アーキテクチャ図-WorldMiniApp案.svg`
  - `ETH_Globalユースケース.pdf`
  ユーザーが明示的に「この資料も見て」と指定した場合にだけ読む。その場合は使ったことを報告する。
- ディレクトリが存在しない／アクセスできない場合は、勝手に別の場所へ書かず、ユーザーにパスを確認する。
- ユーザーが `docs/idea.jpg` のような相対パスを渡した場合は、**`$DOCS_DIR` 起点として解決する**（`$DOCS_DIR/idea.jpg`）。

## 1. 対象を決める

ユーザーが対象（ファイル / ディレクトリ）を指定していればそれを使う。指定が無ければ `$DOCS_DIR/` 全体を対象にする。

```bash
ls -R "$DOCS_DIR"
```

- 対象がディレクトリなら、その配下のファイルを再帰的に列挙してすべて入力候補にする。
- `$DOCS_DIR/requirements/` 自体は入力から除く（既存の出力は更新時の差分確認にだけ使う）。
- 対象が曖昧で候補が複数ある場合（例: 同じ構想の案が複数ある図）は、どれを前提にするかをユーザーに確認する。**勝手に一方を選ばない。**

## 2. 資料を読む

| 種類 | 読み方 |
|------|--------|
| Markdown / テキスト | そのまま読む |
| PDF | Read の `pages` 指定で **全ページ** 読む（10ページ超は必須。20ページずつ分割） |
| SVG | テキストを抽出: `grep -o '<text[^>]*>[^<]*' "$DOCS_DIR/<file>.svg" \| sed 's/<[^>]*>//'`。構造が読めなければ Read で画像として見る |
| PNG / JPG | Read で画像として見る |
| Excel / CSV | CSV は `cat`、xlsx は変換できなければユーザーに中身を確認する |
| ソースコード | 既存実装がある場合のみ、現状仕様の確認として参照する |

読めなかったファイルは、握りつぶさず「前提・参照資料」に**読めなかった旨**を書く。

## 3. 要件を分解する

資料の記述を、次の 5 レベルに **分解** する。1 文に複数の要求が混ざっている場合は必ず分割する（「〜し、かつ〜できる」→ 2 件）。

| レベル | ID | 内容 |
|---|---|---|
| ビジネス要求 | `BR-001` | なぜ作るか。解決したい課題・提供価値・成功指標（KPI） |
| 利用者・ユースケース | `UC-001` | 誰が、どういう状況で、何を達成するか |
| 機能要件 | `FR-001` | システムが提供する振る舞い。画面・API・バッチ・イベント単位 |
| 非機能要件 | `NFR-001` | 性能 / 可用性 / セキュリティ / 運用 / 拡張性 / UX / 法規制 |
| 制約 | `CON-001` | 技術スタック・予算・期限・外部サービス・チェーンやネットワークの前提 |

分解の手順:

1. **抜き出す** — 資料の一文一文から要求らしき記述を拾い、出典（ファイル名・ページ/行）を必ず紐づける。
2. **分割する** — 複合文を単一の要求に割る。1 要件 = 1 検証可能な文。
3. **正規化する** — 「〜できること」「〜すること」の形に揃える。曖昧語（速い・使いやすい・大量の）は測定可能な値に置き換え、値が資料に無ければ **仮置きして未決事項に上げる**。
4. **重複を潰す** — 同じ要求の言い換えは 1 件に統合し、統合元の出典をすべて残す。
5. **欠落を補う** — 各ユースケースについて、正常系だけでなく **異常系・権限・データ保持/削除・監査ログ・エラー通知** が定義されているか点検する。抜けは「未決事項」か「推定要件（要確認）」として明示する。

## 4. 解析する

分解した要件を突き合わせて、次を判定する:

- **優先度**: MoSCoW（`Must` / `Should` / `Could` / `Won't`）。ハッカソン・MVP なら「初回リリース対象か」を基準にする。
- **依存関係**: 「FR-003 は FR-001 の完了が前提」など。循環していないか確認する。
- **矛盾・競合**: 資料間で食い違う記述（例: 図 A と仕様文）は、片方を採用せず **両方を併記して未決事項に上げる**。
- **実現性リスク**: 外部サービス依存、未確定の API、規制、性能上の懸念。
- **スコープ外**: 今回やらないことを `OUT-001` として明示する。書かないと後で揉める。

**推測で埋めない。** 資料から読み取れない点は「未決事項（`Q-001`）」に列挙し、要件本文には「（仮）」と付けて扱いを明記する。

## 5. 出力する

出力先は **`$DOCS_DIR/requirements/analysis.md`**（1 ファイルのみ。要件定義書やトレーサビリティ表はここでは作らない）。

```bash
mkdir -p "$DOCS_DIR/requirements"
```

**ID はこのスキルで確定させる。** 既に `$DOCS_DIR/requirements/requirements.md` がある場合は必ず先に読み、**既存の ID を再利用して振り直さない**（廃止する要件は行を残して「廃止」と記す）。新規分だけ最大番号の続きから採番する。

### 5-1. `analysis.md` の書き方

```markdown
# 要件分解・解析メモ

> 対象資料: <読んだファイル名>
> 資料の置き場所: /mnt/c/second-brain/ethglobal_hackathon/docs
> 最終更新: YYYY-MM-DD

## 1. 読んだ資料
| 資料 | 種別 | 読んだ範囲 | 読めなかった箇所 |

## 2. 抽出した記述（生データ）
資料の記述と、そこから起こした要件 ID の対応。分割した場合は分割前の原文も残す。

| No | 原文（資料の記述そのまま） | 出典 | 起こした要件 |

## 3. 分解結果

- 図に描くべきアクターと UC のまとまり（領域分けの案）
```

各章には、**表だけでは伝わらない構造がある場合に限り** SVG の図を作って埋め込む（5-2 参照）。


既存の `analysis.md` があれば上書きではなく **差分更新** とし、変更点を末尾の「変更履歴」に追記する。

### 5-2. 章ごとの図（SVG）

**各章について、表だけでは伝わらない構造があれば SVG の図を作り、その章に埋め込む。**
図ありきで作らない — 表で足りるなら作らない。

#### 作るかどうかの判断

図が価値を持つのは、**関係・構造・分布**を示すときに限る。

| 章 | 作る価値が高い図 | 作らなくてよい場合 |
|---|---|---|
| 3. 分解結果 | BR → UC → FR の分解ツリー（どの要求がどこまで降りたか） | 要件が 10 件未満で表を追える |
| 4. 統合・重複 | 複数出典 → 1 要件への集約図 | 統合が 2〜3 件しかない |
| 5. 欠落点検 | UC × 観点（異常系・権限・保持削除・監査ログ・通知）のカバレッジ図 | UC が少なく表で一目で分かる |
| 6-1. 優先度 | MoSCoW の件数内訳と、Must が集中している領域 | 件数が少ない |
| 6-2. 依存関係 | **依存グラフ（DAG）** — 最も価値が高い。循環の有無を目で確認できる | 依存が 5 本未満 |
| 6-3. 矛盾・競合 | 資料 A と資料 B の対立構造と、影響する要件への波及 | 矛盾が 1 件だけ |
| 6-4. 実現性リスク | リスク → 影響する要件 → 未決事項 のつながり | リスクが独立していて連鎖しない |
| 6-5. スコープ外 | MVP / 今後の拡張 / 対象外 のスコープ境界図 | スコープが 1 段階しかない |
| 7. 未決事項 | 未決 1 件が何件の要件を止めているかの波及図 | 未決が少ない |
| 8. 申し送り | 図の領域分け案の俯瞰（どの UC をどの図に入れるか） | 領域分けが不要なほど UC が少ない |

1. と 2. は出典の記録が目的なので、図は基本的に作らない。

#### 置き場所と名前

```bash
mkdir -p "$DOCS_DIR/requirements/img"
```

- ファイル名は **`<章番号>-<内容>.svg`**（章番号はドットをハイフンにする）。例:
  - `img/03-requirement-tree.svg`
  - `img/06-2-dependency-graph.svg`
  - `img/06-3-conflicts.svg`
  - `img/07-open-questions-impact.svg`
- 図を差し替えるときは**同じファイル名を使う**（章とファイルの対応を崩さない）。

#### 埋め込み方

`.svg` ファイルとして保存したうえで、**その中身を `analysis.md` にインラインで埋め込む**。画像リンクだけで済ませない。

- 埋め込み位置は、その図が説明している**章の中**（表の直前か直後）。
- `<svg>` 要素をそのまま本文に書く。前後を空行で挟み、コードフェンスで囲まない。
- 根要素の `xmlns="http://www.w3.org/2000/svg"` を必ず残し、埋め込む側にだけ `style="max-width:100%;height:auto"` を足す。
- 図の直後に `[この図を SVG ファイルで開く](img/<ファイル名>.svg)` を 1 行添える（GitHub はインライン SVG を表示しないため）。
- 図の直前か直後に、**その図が何を示しているかを 1 行**書く。図だけ置かない。
- **インラインの中身は `.svg` ファイルから機械的にコピーする。** Markdown 側を手で編集しない。

#### SVG の書き方（必須ルール）

- ルートは `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 W H" width="W" height="H">`。`viewBox` を必ず付ける。
- 背景に `<rect fill="#ffffff">` を敷き、線と文字は濃色（`#1f2937`）で描く。`currentColor` や CSS 変数に頼らない（ダーク/ライト両対応）。
- フォントは `font-family="'Noto Sans JP','Hiragino Sans','Yu Gothic',sans-serif"`、本文 `font-size="12"`〜`13`。テキストは `<text>` 要素で書き、パス化しない。
- `<style>` 要素は使わず、すべて属性で指定する（Obsidian と GitHub の描画差を避けるため）。
- 矢印は `<defs>` の `<marker>` を定義して再利用する。
- **図に出す要件 ID・名称は `analysis.md` の表と完全に一致させる。** 略称を使わない。
- 節点が 20 を超えて読めなくなる場合は、**上位だけを描くか領域ごとに分割**する。全部を 1 枚に詰めない。
- 線を交差させない。交差しそうなら節点の並び順を入れ替える。


## 6. 検証と報告

出力前に自己点検する:

- [ ] すべての要件に **出典** が付いているか（出典が無い＝推測。「推定要件（要確認）」と明示したか）
- [ ] 1 要件 = 1 検証可能な文になっているか（複合文が残っていないか）
- [ ] 非機能要件が測定可能な表現か（「速い」等が残っていないか）
- [ ] 依存関係に循環が無いか、参照先 ID が実在するか
- [ ] 既存 `requirements.md` の ID を振り直していないか
- [ ] 要件 ID が重複していないか（`grep -oE '\b(BR|UC|FR|NFR|CON|OUT|Q)-[0-9]{3}\b' "$DOCS_DIR"/requirements/*.md | sort | uniq -c` で確認）
- [ ] 資料間の矛盾を握りつぶさず「6-3. 矛盾・競合」に載せたか
- [ ] 保存先が `$DOCS_DIR/requirements/analysis.md` になっているか
- [ ] 図を作った章について、**`.svg` が `$DOCS_DIR/requirements/img/` に保存され、`analysis.md` にインラインで埋め込まれているか**（`grep -c '<svg ' analysis.md` と `ls img/*.svg | wc -l` が一致するか）
- [ ] 埋め込んだ SVG が `img/` のファイルと同じ内容か（`style` 属性の追加以外に差分が無いか）
- [ ] 図の SVG が well-formed か（`python3 -c "import xml.etree.ElementTree as E;E.parse('<path>')"`）
- [ ] 図に出した要件 ID・名称が `analysis.md` の表と一致しているか
- [ ] 表で足りる内容を図にしていないか（figure ありきになっていないか）

最後にユーザーへ短く報告する:

- 作成・更新したファイル（**フルパスで示す**。`analysis.md` と `img/` 配下の図）
- 作った図とその章、作らなかった章とその理由
- 要件件数（種別ごと）と Must の件数
- 主要な解析結果（優先度の判断、矛盾点、スコープ外にしたもの）
- **未決事項の一覧**（ここが一番重要。ユーザーの回答が必要なものを箇条書きで）

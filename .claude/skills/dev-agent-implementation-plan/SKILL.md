# dev-agent-implementation-plan

エージェントの設計を、**1 回ずつ終わらせられる作業の列に分ける**スキル。コードは書かない。

エージェントの実装は、設計資料が 4 種類（オーケストレーション・コンテキスト・プロンプト・インフラ）にまたがり、既存のコードも大きい。一度に実装しようとすると、読む量だけでコンテキストが尽き、途中で判断が雑になる。このスキルは、**後続の `dev-agent-implementation` が 1 回の実行で読む量を最小にできるよう**に、作業を切り分け、各作業で読むべき資料の範囲まで先に決めておく。

- **コードも設計書も書き換えない。** 書くのは作業計画だけ。
- **設計に無い機能を計画に入れない。** 必要だと気づいたら「着手前に決める事項」に上げ、設計スキルへ差し戻す。
- **推測で埋めない。** 設計が未決（`OQ` / `CQ` / `PQ` / `IQ` 等）のまま実装すると作り直しになるものは、決める事項として切り出す。

## 0. 作業ディレクトリ

```bash

DOCS_DIR=/mnt/c/second-brain/ethglobal_hackathon/docs    # 設計書（読む）・計画（書く）
OUT=$DOCS_DIR/implementation                             # 出力先
```

| 種類 | 置き場所 |
|---|---|

| 現状の実装の解析（入力） | `$DOCS_DIR/as-built/as-built-architecture.md`、`design-drift.md` |

| コード（入力） | `$REPO`（**読むだけ。1 行も変更しない**） |
| 作業計画（出力） | **`$OUT/agent-impl-plan.md`** |

コードで必ず確かめる箇所（as-built の記述が今も正しいかを確かめるため）:

```bash
cd $REPO
git rev-parse --short HEAD; git status --porcelain | grep -E '^.. (apps|contracts)/'
ls apps/api/app/services apps/api/app/routers
grep -nE '^def |^class ' apps/api/app/services/gemini.py apps/api/app/services/assign.py apps/api/app/services/worker.py
grep -nE 'bg\.add_task|worker\.enqueue' apps/api/app/routers/*.py
grep -nE '^class |__tablename__' apps/api/app/models.py
ls apps/api/tests 2>/dev/null; grep -n pytest apps/api/requirements.txt
```

### 1-1. as-built の鮮度を確かめる

`as-built-architecture.md` の「基準コミット」と `git rev-parse --short HEAD` を比べる。

- 一致していれば、そのまま使う。
- 違っていれば、`git diff --stat <基準コミット>..HEAD -- apps contracts` を見る。**エージェントに関わるファイル（`services/gemini.py`・`assign.py`・`worker.py`・`routers/cases.py`・`routers/disputes.py`・`models.py`）が変わっていたら**、ユーザーに `dev-implementation-architecture-analysis` を先に実行し直すよう提案する。それでも進める場合は、変わったファイルを自分で読み、計画の「前提」に**as-built が古いこと**を明記する。

### 1-2. 入力が欠けているとき

- `agent-orchestration.md` が無い → **先に `dev-agent-orchestration-design` を実行するよう促す**。これが無いと計画できない。
- `agent-context` / `agent-prompt` / `agent-infra` のどれかが無い → その設計に依存する作業パッケージを「設計待ち」として計画に載せ、どのスキルで設計するかを書く。無いまま実装を計画しない。
- `as-built` が無い → **先に `dev-implementation-architecture-analysis` を実行するよう促す**。現状が分からないとギャップが出せない。

## 2. 計画する

次の順で進める。**飛ばさない。** とくに 2-1 と 2-2 を飛ばすと、既存のコードと衝突する計画になる。

### 2-1. 設計の名前と実装の名前を対応づける

設計資料は、上流のデータ設計の名前（例: `projects`・`pm_agents.policy`・`human_verifications`・`task_escrows`）で書かれている。現状の実装は別の名前で動いている（例: `cases`・`agents.rules`・`world_verifications`・`tasks` の投影列。as-built の DR-010・DR-026）。

**実装がどちらの名前に合わせるかを、計画の最初に決める。** 決め方の既定は次のとおり。

- **既定: 既存の実装の名前に合わせる。** 設計の名前はコードに持ち込まず、対応表で読み替える。既存のテーブルや API を改名すると、フロント・監査ビュー・スクリプトまで波及し、エージェントの実装と関係のない作業が膨らむため。
- 設計の構造が既存に**無い**もの（例: `policy` の `workflow.phases` と `human_roles`）は、既存のテーブルに列を足すか新しいテーブルを作るかを決める事項（2-5）に上げる。
- 改名したほうがよいと判断した場合も、**計画では決めない**。決める事項に上げ、ユーザーの判断を待つ。

対応表は計画書の 3 章に置く（設計の名前 / 実装の名前 / 対応の種類〔同じ・読み替え・無い〕/ 根拠）。

### 2-2. ギャップを洗い出す

設計の ID を**全件**、現状と突き合わせる。対象は `AG` / `TOOL` / `HIL` / `GRD` / `CTX` / `CG` / `PMT` / `INF` / `OPS` と、エージェントに関わる横断事項（観測・コスト・評価）。

各 ID について次を決め、`GAP-001` から採番する。

| 項目 | 内容 |
|---|---|
| 現状 | 実装済 / 一部 / 無し / 形を変えて実装。**根拠はファイル名と行番号**（as-built の記述を転記するだけにせず、コードで確かめる） |
| 必要な作業 | 何を作る・直すか（1〜2 文） |
| 種類 | 新規 / 既存の改修 / 既存の置き換え / 設定・運用 / 対象外 |
| 関わる DR | as-built の `DR-` ID |

- **実装済みのものも表から省かない。** 全体が見えていないと、カバレッジ（2-7）が確かめられない。
- **「対象外」にする場合は理由を書く**（例: 設計が未決、ハッカソンの範囲外とユーザーが決めた、上流の変更待ち）。
- 既存のコードが設計と**別の形で同じ目的を果たしている**場合（例: `services/gemini.py` の `plan_case` と AG-002）は、「置き換える」か「改修して寄せる」かを書く。置き換えるなら、**既存の呼び出し元を洗い出す**（`grep -rn '<関数名>' apps`）。

### 2-3. 作業パッケージに分ける

ギャップを `WP-001` から採番した作業パッケージにまとめる。

**1 つの WP の大きさの目安**（1 回の `dev-agent-implementation` で、読む・書く・テストするが終わる大きさ）:

| 目安 | 上限 |
|---|---|
| 触るファイル | 5 ファイル程度（テストを除く） |
| 変更量 | 追加・変更で 400 行程度 |
| 読む設計資料 | 章・ID を指定して 3〜4 か所（**資料をまるごと読ませない**） |
| 完了の確かめ方 | その WP だけで完結するテストかコマンドがある |

**分け方の原則**:

- **縦に切る。** 「AG-002 のタスク分解を、コンテキストの組み立てから出力の検証・保存まで通す」のように、1 つの WP で動くものが 1 つ増える単位にする。「全エージェントのプロンプトだけ」のような横切りは、共通の土台（2-4 の Phase 0）に限る。
- **1 つの WP に不可逆な操作を 2 つ入れない。** 送金（TOOL-009）・オンチェーンへの書き込み・DB スキーマの変更は、それぞれ単独の WP にする。
- **既存の挙動を置き換える WP は、切り替えを別の WP にする。** 「新しい実装を並べて作り、テストで同じ結果を確かめる WP」と「呼び出し元を切り替えて古い実装を消す WP」に分ける。途中で止まっても、動いている状態が保たれる。
- **DB スキーマを変える WP は、マイグレーションの方法を決めてから置く。** 現状は `create_all` と手書きの `_migrate()` しか無い（as-built DR-013）。方法が未決なら 2-5 に上げる。
- 目安を超える WP は分ける。分けられない場合は、その理由を WP に書く。

### 2-4. 順序と依存を決める

依存の向きに沿って並べる。**循環したら WP の切り方が間違っている。** 切り直す。

典型的な順序（設計と現状に合わせて調整してよい。**この順序を理由なく崩さない**）:

| Phase | 内容 | 例 | 先に置く理由 |
|---|---|---|---|
| 0 | 共通の土台 | LLM 呼び出しの共通層（構造化出力・再試行・トークン計測）、ツールの実行基盤と権限（GRD-001）、コンテキストの組み立てとガード（CTX / CG）、プロンプトの読み込みと版（PMT の版管理）、記録（12 章）、**テストの土台**（現状 API のテストが無い。as-built AR-X11） | 以降のすべての WP がこれに乗る |
| 1 | 停止と上限 | キルスイッチ（GRD-007 / OPS-001・002）、コスト上限（GRD-005）、反復と時間の上限（11 章） | **エージェントが動く前に止められる状態にする** |
| 2 | 参照だけのエージェント | 論点整理（AG-004）・タスク分解（AG-002）など、副作用が可逆な保存だけのもの | 失敗しても戻せる |
| 3 | 外部を参照するエージェント | チーム編成（AG-003。ENS の候補検索 TOOL-002、予算の検証 GRD-002） | 外部連携と決定的な検証が要る |
| 4 | オーケストレータ | AG-001 の委譲・状態・再開（10 章）・人間の介在点（HIL）へのつなぎ込み | 委譲先がそろってから |
| 5 | 不可逆な操作 | 送金の実行（TOOL-009）と、その前提のガード（GRD-009〜011）、IF-024 | **Phase 1 のキルスイッチと、GRD-009〜011 の決定的な検証が入るまで着手しない** |
| 6 | 評価と運用 | 評価セットと回帰（agent-context 11 章・agent-prompt 8 章）、運用手順の実装（OPS）、インフラの分離（INF） | 動くものがそろってから測る |

- 既存の画面や API が今の関数（例: `gemini.plan_case`）を使っている場合、**切り替えの WP までは既存の挙動を壊さない**ことを依存に書く。
- インフラの分離（例: 署名ワーカー INF-003 の別プロセス化。as-built DR-003）のように規模が大きく、エージェントの動作に必須でないものは、Phase 6 に置くか、決める事項（2-5）に上げてユーザーに範囲を決めてもらう。

### 2-5. 着手前に決める事項を切り出す

**決まっていないと作り直しになるもの**を `DEC-001` から採番して一覧にする。各事項に「決まらないと着手できない WP」を書く。

最低限、次を確かめる:

| 確認すること | 決まっていないと何が起きるか |
|---|---|
| 設計の名前と実装の名前のどちらに合わせるか（2-1） | テーブル・API の形が決まらない |
| Agent の定義（`policy`）の置き場所と形（DB の列か、ENS か。as-built DR-010） | AG-001〜003 のコンテキスト（CTX-004）の入力が決まらない |
| マイグレーションの方法（as-built DR-013） | スキーマを変える WP に着手できない |
| LLM ジョブの実行方式（BackgroundTasks のままか、`chain_jobs` のようなジョブ基盤か。as-built DR-014、agent-infra 4 章） | 状態と再開（agent-orchestration 10 章）の実装が決まらない |
| 使うモデルと上限の数値（`CQ` / `OQ` の仮置き。GRD-003〜005） | 上限の定数とトークン予算が決まらない |
| 送金の起動を誰がするか（IF-024。as-built DR-012） | TOOL-009 の呼び出し元が決まらない |
| インフラの分離をどこまでやるか（INF-002 / INF-003） | Phase 6 の範囲が決まらない |

- 設計書の未決事項（`OQ` / `CQ` / `PQ` / `IQ`）のうち、実装に影響するものは**すべて**ここに転記する。影響しないものは載せない。
- 事項ごとに**推奨案と、その理由**を 1 つ書く（ユーザーが判断しやすくするため）。ただし決めるのはユーザー。

### 2-6. 各 WP の中身を書く

WP ごとに次を書く。**「読む資料」と「触るファイル」は具体的に書く。** 後続のスキルはこれ以外を原則読まない。

| 項目 | 書き方 |
|---|---|
| 目的 | この WP が終わると何ができるようになるか（1 文） |
| 対象の設計 ID | AG / TOOL / GRD / CTX / CG / PMT / HIL / INF / OPS と、解消する GAP・DR |
| 依存 | 先に終わっている必要がある WP と DEC |
| 読む資料 | ファイル名と章、または ID（例: `agent-orchestration.md` 6-3 の TOOL-004、`prompt-library.md` の PMT-002・PMT-006・PMT-014）。**行範囲が分かれば書く**（`grep -n` で見出しの行を調べる） |
| 読むコード | ファイル名と関数名（例: `apps/api/app/services/gemini.py` の `plan_case`） |
| 触るファイル | 新規・変更の別をつけて列挙 |
| 作業手順 | 3〜7 手順。設計の ID を手順に紐づける |
| 完了条件 | 観測できる形で書く（例: 「予算超過の出力が保存されず、再試行が 3 回で HIL-005 に渡ることをテストで示す」） |
| 検証方法 | 実行するコマンド（例: `cd apps/api && .venv/bin/python -m pytest tests/test_xxx.py -q`） |
| 戻し方 | うまくいかなかったときに元へ戻す方法（例: 新しいモジュールを消すだけ、フラグで旧実装に戻す） |
| 規模 | S / M / L（L は分けられない理由を書く） |
| 状態 | `未着手`（後続スキルが `進行中` / `完了` / `保留` に更新する） |

### 2-7. カバレッジを確かめる

設計の ID の全件が、いずれかの WP に割り当たっているか、「対象外」として理由が書かれているかを確かめる。

```bash
for f in agent-orchestration/agent-orchestration.md agent-context/agent-context.md agent-prompt/agent-prompt.md agent-infra/agent-infra.md agent-infra/infra-runbook.md agent-prompt/prompt-library.md; do
  grep -oE '\b(AG|TOOL|HIL|GRD|CTX|CG|PMT|INF|OPS)-[0-9]{3}\b' "$DOCS_DIR/$f"; done | sort -u > /tmp/design-ids.txt
grep -oE '\b(AG|TOOL|HIL|GRD|CTX|CG|PMT|INF|OPS)-[0-9]{3}\b' "$OUT/agent-impl-plan.md" | sort -u | comm -23 /tmp/design-ids.txt -
```

（`/tmp` ではなく、この会話のスクラッチパッドのディレクトリを使う。）最後のコマンドの出力が空であること。

## 3. 出力する

**`$OUT/agent-impl-plan.md` を 1 つだけ作る。** 無ければディレクトリを作る（`mkdir -p "$OUT"`）。既存の計画があれば読み、**差分更新**する。

- 既存の `WP-` / `GAP-` / `DEC-` の ID は**振り直さない**。不要になった WP は行を残して状態を「廃止」にする。
- `完了` の WP の中身は書き換えない。設計が変わって作り直しが要る場合は、新しい WP を足す。
- 変更履歴に、何を足し・何を変えたかを書く。

```markdown
# エージェント実装計画

> 基準コミット: <short sha>（<ブランチ>）
> 参照した設計: agent-orchestration.md（最終更新 YYYY-MM-DD）、agent-context.md（…）、agent-prompt.md（…）、agent-infra.md（…）
> 参照した現状: as-built-architecture.md（基準コミット <sha>）、design-drift.md
> 最終更新: YYYY-MM-DD

## 1. 概要
```

## 4. 検証と報告

出力前に自己点検する:

- [ ] 設計の ID を**全件**、ギャップ一覧かカバレッジに載せたか（2-7 のコマンドの出力が空か）
- [ ] 「現状」の根拠を、as-built の転記ではなくコードで確かめたか（ファイル名と行番号があるか）
- [ ] as-built の基準コミットと HEAD を比べたか。違う場合、その旨を前提に書いたか
- [ ] すべての WP に「読む資料（章・ID の指定）」「触るファイル」「完了条件」「検証方法」「戻し方」があるか
- [ ] 目安（5 ファイル・400 行・資料 3〜4 か所）を超える WP を分けたか。分けられないものに理由を書いたか
- [ ] 不可逆な操作（送金・オンチェーン書き込み・スキーマ変更）が、それぞれ単独の WP になっているか
- [ ] 送金の WP が、キルスイッチ（GRD-007）と送金のガード（GRD-009〜011）の WP に依存しているか
- [ ] 既存の挙動を置き換える WP が、「並べて作る」と「切り替える」に分かれているか
- [ ] 依存に循環が無いか
- [ ] 実装に影響する未決事項（`OQ` / `CQ` / `PQ` / `IQ`）を、すべて決める事項に転記したか
- [ ] 設計に無い機能を WP に入れていないか
- [ ] コードと設計書を変更していないか（`git -C $REPO status --porcelain` が着手前と同じか）
- [ ] 保存先が `$OUT/agent-impl-plan.md` か（`$REPO/docs/` に書いていないか）
- [ ] Mermaid の構文が正しいか（`npx -y @mermaid-js/mermaid-cli` で描画できればする。できなければ目視で確かめ、未検証と報告する）

最後にユーザーへ短く報告する:

- 作成・更新したファイル（フルパス）と基準コミット
- WP の数と Phase ごとの内訳、**最初に着手する WP**
- **決める事項（DEC）の一覧**と、それぞれの推奨案。とくに**最初の WP を止めているもの**
- ギャップの要約（設計の ID のうち、実装済・一部・無しが何件か）
- 対象外にした ID と理由

## 5. 後続への引き渡し

- 決める事項に回答をもらったら、この計画の 5 章を「決定: 内容」に更新してから実装に進む。
- 実装は **`dev-agent-implementation`** で、原則 1 回に 1 WP ずつ進める（「WP-003 を実装して」「次の WP を実装して」）。
- 計画の途中で設計の不足・矛盾が見つかったら、**`dev-agent-orchestration-design` / `dev-agent-context-design` / `dev-agent-prompt-design` / `dev-agent-infra-design` に戻して設計側を直す**。計画側で辻褄を合わせない。
- 大きく実装が進んだら、`dev-implementation-architecture-analysis` で as-built を更新し、このスキルで計画を見直す。

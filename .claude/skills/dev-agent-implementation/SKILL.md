# dev-agent-implementation

作業計画の WP を、**1 つずつ、動いてテストが通る状態で積み上げる**スキル。

一度にたくさん実装しない。1 回の実行で読む量を抑え、1 つの WP を最後（テストと記録）までやり切ってから止まる。途中で止まっても、次の実行がこの記録から続きを始められるようにする。

- **計画に書かれた範囲だけを実装する。** 計画に無い機能・設計に無い機能を足さない。
- **設計書と計画の中身（WP の定義）を書き換えない。** 書き換えてよいのは、計画の**状態の列**と、実装記録だけ。
- **推測で埋めない。** 着手前に決める事項（DEC）が未決なら、その WP には着手しない。

## 0. 作業ディレクトリ

```bash
REPO=/home/million/team_codrea_ethglocal                 # コードとテスト（書く）
DOCS_DIR=/mnt/c/second-brain/ethglobal_hackathon/docs    # 設計書（読む）
PLAN=$DOCS_DIR/implementation/agent-impl-plan.md         # 作業計画（読む・状態だけ更新）
LOG=$DOCS_DIR/implementation/agent-impl-log.md           # 実装記録（書く）
```

| 種類 | 置き場所 |
|---|---|
| エージェントのコード・プロンプトの定数・テスト | **`$REPO`**（主に `apps/api/app/` と `apps/api/tests/`） |
| 設計書 | `$DOCS_DIR/agent-*/`（**読むだけ**） |
| 作業計画 | `$PLAN`（**状態の列と WP の「状態」行だけ**を更新） |
| 実装記録（設計との対応・逸脱・テスト結果・図） | **`$LOG`** |
| 実装記録の図（SVG） | **`$DOCS_DIR/implementation/img/`**（`$LOG` にインラインで埋め込む。5-3） |

- `$DOCS_DIR` は Obsidian の vault。改行は LF、UTF-8。**`$REPO/docs/` は vault ではない。ここに記録を書かない。**
- **秘密情報をリポジトリに置かない。** API キー・秘密鍵・接続文字列はコードに書かず、`apps/api/app/config.py` の設定として読む。新しい設定を足したら `apps/api/.env.example` に**プレースホルダだけ**を書く。`.env` は開かない。
- **コミットと push は求められたときだけ行う。**

## 1. 対象の WP を決める

```bash
test -f "$PLAN" || echo "計画が無い"
grep -nE '^\| WP-[0-9]{3} ' "$PLAN"          # 一覧と状態
grep -nE '^\| DEC-[0-9]{3} ' "$PLAN"         # 決める事項と状態
```

- **計画が無ければ、先に `dev-agent-implementation-plan` を実行するよう促して止まる。** 計画なしで実装しない。
- ユーザーが WP を指定したら、それを対象にする。指定が無ければ、**依存がすべて `完了` で、状態が `未着手` の WP のうち番号が最も小さいもの**を選ぶ。`進行中` の WP があれば、それを優先して再開する。
- 対象の WP について、次を確かめる。1 つでも満たさなければ**着手せずに**理由を報告して止まる。
  - 依存する WP がすべて `完了` である
  - 依存する DEC がすべて「決定」になっている（未決なら、その DEC の選択肢と推奨案をユーザーに示して判断を求める）
  - 作業ツリーに、この WP と関係のない未コミットの変更がアプリのコード（`apps/` `contracts/`）に無い。あればユーザーに確認する（他の作業を巻き込まないため）
- **1 回に 1 WP が原則。** ユーザーが複数を指定した場合も、1 つ終えるごとに 4 章の検証と 5 章の記録を済ませてから次へ進む。規模 S の WP が続く場合に限り、2 つまで続けてよい。

## 2. 読む

**計画の対象 WP の節に書かれた「読む資料」と「読むコード」だけを読む。** 設計資料をまるごと読まない。

```bash
# 計画から対象 WP の節だけを取り出す
awk '/^### WP-003 /{f=1} /^### WP-/{if(f&&!/^### WP-003 /)exit} f' "$PLAN"
# 設計資料は、指定された章や ID の前後だけを読む
grep -nE '^#{2,3} |TOOL-004' "$DOCS_DIR/agent-orchestration/agent-orchestration.md"   # 行番号を調べてから
# → Read ツールで offset / limit を指定して、その範囲だけを読む
```

- プロンプトの本文（`prompt-library.md`）は、**この WP が扱う PMT の節だけ**を読む。
- 前の WP で作った共通の土台は、**使い方（関数のシグネチャとテスト）だけ**を読む。中身を読み直さない。
- 実装記録 `$LOG` は、依存する WP の節だけを読む（その WP で決めたこと・逸脱を引き継ぐため）。
- **計画に書かれていない資料が必要になったら**、読んでよいが、何を追加で読んだかを実装記録に書く。追加で読む量が多くなりそうなら、それは WP の切り方が合っていない。止めて、計画の見直し（`dev-agent-implementation-plan`）を提案する。

## 3. 実装する

計画の「作業手順」に沿って進める。各手順を設計の ID に紐づけ、コードのコメントやテスト名に ID を残す（例: `# GRD-002: 予算超過は保存しない`、`test_grd002_rejects_over_budget`）。

### 3-1. 設計から外れない

次は設計書のとおりに実装する。変えたくなったら、実装で変えずに記録し、上流へ差し戻す。

| 対象 | 設計書 |
|---|---|
| エージェントの入出力・使えるツール・担わないこと・停止条件・失敗時の挙動 | `agent-definitions.md` の各 AG |
| ツールの名前・入出力スキーマ・可逆性・冪等キー | `agent-orchestration.md` 6-2・6-3 |
| ガードレールの判定（**モデルではなく決定的なコードで判定する**） | `agent-orchestration.md` 8 章・9-2 |
| コンテキストのブロック構成・並び順・予算・切り詰めの順序 | `agent-context.md` 4〜6 章、`context-templates.md` |
| 信頼できない入力の扱い（区切り・位置・正規化・長さ・出力の検証・再投入の禁止） | `agent-context.md` 7 章の CG |
| プロンプトの本文と版 | `prompt-library.md` の PMT（**本文を勝手に言い換えない**。版を上げる必要があれば記録して差し戻す） |
| 記録する項目・記録してはいけない項目 | `agent-orchestration.md` 12 章、`agent-infra.md` 8 章 |

**設計の名前と実装の名前は、計画の 3 章の対応表に従って読み替える。** 対応表に無い名前が必要になったら、勝手に決めずに止めて報告する。

### 3-2. 守ること

- **モデルの出力を信じない。** 構造化出力をスキーマで検証し、副作用（保存・送信）の前に決定的なコードで検証する（CG-005、9-2）。
- **エージェントに渡すツールは、そのエージェントに許されたものだけ**にする（GRD-001）。権限はプロンプトの文言ではなく、ツールの実行基盤で縛る（CG-006）。
- **信頼できない入力（依頼文・紛争の主張・ENS の値・定義データの自由文）は、指示より後ろに、区切って置く**（CG-001〜004）。ENS の自由文をコンテキストに入れない（CG-008）。
- **再試行のときに、前回のモデル出力をコンテキストに戻さない。** 違反項目だけを渡す（CG-007）。
- **金額と送金先をエージェントに決めさせない・渡さない**（AG-001、TOOL-009、GRD-009〜011）。
- **記録してはいけないもの**（World の検証に伴う個人識別情報、鍵・API キー、プロンプトに含まれる秘密）をログに出さない。
- **既存の挙動を壊さない。** 計画が「並べて作る」WP なら、既存の関数と呼び出し元は変えない。「切り替える」WP だけが呼び出し元を変える。
- **LLM の呼び出しはテストで本物を叩かない。** 既存のモック（`GEMINI_API_KEY` が空のときの決定的な応答。`apps/api/app/services/gemini.py`）か、テスト用の差し替えを使う。
- 既存のコードの書き方（命名・コメントの密度・日本語のドキュメント文字列・モックへの切り替え方）に合わせる。
- **import はモジュールの先頭にまとめる。関数・メソッドの中で `import` / `from ... import` を書かない**（ユーザー指示 2026-09-26）。テストの `conftest.py` のように、環境変数を設定してからでないと import できないものは、設定の直後のモジュールの先頭側に置き `# noqa: E402` を付ける。循環 import が避けられない場合は、関数の中に逃がさずにモジュールの分け方を見直し、どうしても必要なら理由を実装記録に書いてユーザーに確認する。

### 3-3. 不可逆な操作を含む WP

送金（TOOL-009）・オンチェーンへの書き込み・DB スキーマの変更を含む WP では、次を**追加で**守る。

- 実装の前に、**その操作を止める手段がすでに動いていること**を確かめる（キルスイッチ GRD-007 の WP が `完了` であり、テストが通っている）。
- **テストネット・モックでだけ動かす。** 実チェーンで送信するテストはユーザーの明示的な指示があるときだけ行う。
- DB スキーマの変更は、計画の DEC で決めたマイグレーションの方法に従う。既存のデータを消す変更をしない。
- 完了条件に「拒否されるべき呼び出しが拒否されること」を必ず含める（例: HIL-002 の承諾が無い案件への送金が拒否される）。

### 3-4. WP が大きすぎると分かったとき

途中で、計画の目安（5 ファイル・400 行程度）を大きく超えると分かったら、**そこで止める。**

1. できたところまでをテストが通る状態にする（通らない部分は元に戻す）。
2. 計画の状態を `進行中` にし、実装記録に「どこまでできたか」と「残り」を書く。
3. 計画の分割（`dev-agent-implementation-plan` での見直し）をユーザーに提案する。**このスキルで WP を勝手に分割・追加しない。**

## 4. 検証する

計画の「完了条件」と「検証方法」をそのまま実行する。加えて、次をすべて確かめる。

```bash
cd $REPO/apps/api
.venv/bin/python -m pytest -q                         # 既存と今回のテストがすべて通る
.venv/bin/python -c "import app.main"                 # API が import できる（起動時のエラーが無い）
git -C $REPO status --porcelain                       # 触ったファイルが計画の「触るファイル」と一致する
git -C $REPO diff --stat
```

- `.venv` が無い・`pytest` が入っていない場合は、**入れてよいかをユーザーに確認する**（`apps/api/requirements.txt` には `pytest` が宣言されている）。
- フロント（`apps/web`）を触った WP では `cd $REPO/apps/web && pnpm build` を実行する。
- 完了条件のうち、テストで示せないもの（例: 実チェーンでの動作）は、**何を確かめていないか**を記録に書く。確かめていないものを「完了」とは言わない。
- テストが通らない場合は、原因を直す。直せない場合は WP を `進行中` のままにし、失敗の出力を記録に残して報告する。**失敗しているのに完了にしない。**

## 5. 記録する

### 5-1. 計画の状態を更新する

`$PLAN` の 6 章の表と、7 章の対象 WP の「**状態**」行だけを更新する（`未着手` → `進行中` / `完了` / `保留`）。**WP の中身（目的・手順・完了条件）は書き換えない。** 変更履歴に 1 行足す。

### 5-2. 実装記録を書く

`$LOG` に WP ごとの節を追記する。無ければ作る。

```markdown
# エージェント実装記録

> 計画: `agent-impl-plan.md`
> 最終更新: YYYY-MM-DD

## WP-001 <名前>

- **状態**: 完了 / 進行中 / 保留
- **日付**: YYYY-MM-DD
- **実装したコミット**: <short sha（コミットしていなければ「未コミット」）>
- **対象の設計 ID**: <計画と同じ>

### 変更したファイル
| ファイル | 新規/変更 | 内容 |

### 変更点の図
（この WP で足した・変えたモジュールと、既存のモジュールとの依存を示す SVG。1 行の説明 + インライン埋め込み + `[図を SVG で開く](img/wp-001-changes.svg)`。5-3）

### 実装したロジック
（この WP で実装した処理の流れを Mermaid で。**検証・再試行・失敗時の分岐・停止の確認・保存を省かない**。図の前に「何を示す図か」を 1 行。5-3）

### 設計との対応
| 設計の ID | 実装 | 一致 |
（ツールのスキーマ・ガードの判定・コンテキストの並び・プロンプトの版を 1 件ずつ）

### 設計からの逸脱
| 箇所 | 設計 | 実装 | 理由 | 差し戻し先 |
（**無い場合も「無し」と書く**）

### 検証
| 完了条件 | 確かめ方 | 結果 |
- 実行したコマンドと結果（通過件数）
- **確かめていないこと**

### 追加で読んだ資料
（計画の「読む資料」以外に読んだものがあれば）

### 次の WP への引き継ぎ
（後続の WP が知っておくべき関数・設定・制約。**次の実行はここを読んで始める**）
```

### 5-3. 図を作る

**実装記録には、WP ごとに必ず図を付ける。** 表と文章だけでは、何がどこに増えて、どういう順で動くのかが伝わらないため。図はコードを読んで描く（計画や設計書の図を写さない）。

| 図 | 形式 | 置き場所 | 何を示すか | 作らなくてよい場合 |
|---|---|---|---|---|
| **変更点の図** | SVG | `$DOCS_DIR/implementation/img/wp-<番号>-changes.svg`（例: `wp-004-changes.svg`） | この WP で**新規に足した**・**変更した**モジュール（ファイル）と、それが依存する既存のモジュール・外部システム・DB テーブル。依存の向きを矢印で | **作らなくてよい場合は無い**（必ず作る） |
| **実装したロジック** | Mermaid（```` ```mermaid ````） | `$LOG` の本文 | この WP で実装した処理の流れ。エージェントの委譲・ツール呼び出し・検証（CG-005 / 9-2）・再試行（CG-007）・停止と上限の確認（GRD-007 / GRD-005）・失敗時の行き先（HIL-005 等）・保存 | テストの土台や設定だけの WP で、処理の流れが無い場合（その旨を 1 行書く） |
| 補助図 | SVG（`wp-<番号>-<主題>.svg`）または Mermaid | 同上 | コンテキストの並び・状態遷移・データの形など、上の 2 つで表せないもの | 上の 2 つで足りる場合 |

- 振る舞い（処理の順序・分岐・状態遷移）は **Mermaid**（`flowchart` / `sequenceDiagram` / `stateDiagram-v2`）、構造（モジュールと依存）は **SVG** にする。**SVG で処理の流れを手描きしない。**
- 図の中の名前は、コードの**ファイル名・関数名・テーブル名**と、設計の **ID**（AG / TOOL / GRD / CTX / CG / PMT / HIL）をそのまま使う。図だけの略称を作らない。

**変更点の図（SVG）の記法**:

| 要素 | 記法 |
|---|---|
| この WP で新規に足したモジュール | 角丸矩形・**緑の枠**（`#16a34a`）・淡い緑の塗り（`#f0fdf4`）。中にファイル名（`app/agents/llm.py`）と主な関数名 |
| この WP で変更した既存のモジュール | 角丸矩形・**橙の枠**（`#ea580c`）・淡い橙の塗り（`#fff7ed`）。中に何を変えたかを 1 行 |
| 変更していない既存のモジュール | 角丸矩形・灰色の枠（`#9ca3af`）・白の塗り |
| テスト | 角丸矩形・破線の枠。検証しているモジュールへ破線の矢印 |
| 外部システム・DB テーブル | 角丸矩形 + `&#171;system&#187;` / `&#171;table&#187;` のステレオタイプ |
| 依存（import・呼び出し） | 実線の矢印。**向きを必ず付ける**。線に何を呼ぶかをラベルで書く |
| 凡例 | 図の下部に必ず置く |

- **人間でないものを棒人間で描かない**（World・ENS・Escrow・LLM・エージェントは箱）。
- SVG の書き方と埋め込み方は `dev-architecture-design` スキルの 3-4 に従う（`viewBox` 必須、白の背景、`<style>` を使わない、`«»` は実体参照、`id` は図ごとに一意〔例: `wp004-arrow`〕、`.svg` ファイルから機械的にコピーしてインライン埋め込み、埋め込み側にだけ `style="max-width:100%;height:auto"`、直後に `[図を SVG で開く](img/<ファイル名>.svg)`）。
- 見た目を確かめる。PNG にして崩れ（文字のはみ出し・線の重なり）が無いかを見る。WSL に日本語フォントが無いので Windows のフォントを使う（出力先はスクラッチパッド）:

```bash
npx -y @resvg/resvg-js-cli --no-system-font --font-file /mnt/c/Windows/Fonts/NotoSansJP-VF.ttf \
  --font-default-family "Noto Sans JP" --font-sans-serif-family "Noto Sans JP" <svg> <scratchpad>/<name>.png
```

## 6. 報告する

最後にユーザーへ短く報告する:

- 実装した WP と状態（完了 / 進行中 / 保留）
- 変更したファイル（`$REPO` からの相対パス）と、更新した計画・記録・図（フルパス）
- **テストの結果**（件数と通過数、実行したコマンド）と、**確かめていないこと**
- **設計からの逸脱**（無ければ「無し」と明言する）と、差し戻しが要るもの
- **次に着手できる WP**と、それを止めている DEC があればその内容
- コミットはしていないこと（求められた場合はコミットの内容）

## 7. 自己点検

報告の前に確かめる:

- [ ] 対象の WP の依存と DEC がすべて満たされていることを、着手前に確かめたか
- [ ] 計画に書かれた範囲の資料だけを読んだか（追加で読んだものを記録したか）
- [ ] 計画に無い機能・設計に無い機能を足していないか
- [ ] ガードレールの判定を、プロンプトではなく決定的なコードで実装したか
- [ ] エージェントに許されていないツールを渡していないか（GRD-001）
- [ ] 信頼できない入力を区切り、指示より後ろに置いたか（CG-001・002）。再試行で前回の出力を戻していないか（CG-007）
- [ ] 金額と送金先をエージェントの入力にも出力にもしていないか
- [ ] 秘密情報をコード・ログ・記録に書いていないか。新しい設定は `.env.example` にプレースホルダだけを書いたか
- [ ] テストで本物の LLM・本物のチェーンを叩いていないか
- [ ] 既存のテストを含め、すべて通ったか。API が import できるか

## 8. 後続への引き渡し

- 次の WP は、同じスキルで「次の WP を実装して」と頼めば続きから始められる。
- 設計の不足・矛盾が見つかったら、**実装で辻褄を合わせず**、該当する設計スキル（`dev-agent-orchestration-design` / `dev-agent-context-design` / `dev-agent-prompt-design` / `dev-agent-infra-design`）へ差し戻す。
- WP の切り方が合わないと分かったら、`dev-agent-implementation-plan` で計画を見直す。
- Phase の区切りなど大きく進んだら、`dev-implementation-architecture-analysis` で as-built を更新するよう提案する。

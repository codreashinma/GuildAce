# dev-database-design

アーキテクチャで決めた**データの配置**を、実装できるスキーマに落とすスキル。

**オフチェーンとオンチェーンの両方を設計する。**

- オフチェーン: テーブル定義（列・型・キー・制約・インデックス）
- オンチェーン: コントラクトの状態（struct / mapping / enum）、イベント定義、**ENS などのメタデータ構成**

ここでは**要件もアーキテクチャも新しく作らない**。必要になったら推測で埋めずに未決事項へ上げ、`dev-requirements-spec` / `dev-architecture-design` に差し戻す。

- 出力先: `$DOCS_DIR/database/`（Markdown）／`$DOCS_DIR/database/img/`（**ER 図の SVG はすべてここに置く**）
- このディレクトリは **Obsidian の vault**（Windows 側 `C:\second-brain`）を WSL からマウントしたもの。以下に注意する:
  - `.obsidian/` 配下と `*:Zone.Identifier` は入力から除外する。
  - 改行は LF、文字コードは UTF-8 で書く。
  - Obsidian で開けるよう、**見出し・テーブル・チェックリスト・コードブロックは標準の Markdown 記法**に収める。
- **解析対象から除外するファイル**（ユーザー指示 2026-09-25。読み込まない・出典にも使わない）:

  ユーザーが明示的に「この資料も見て」と指定した場合にだけ読む。その場合は使ったことを報告する。

## 1. 入力を読む

| 入力 | 扱い |
|------|------|
| `$DOCS_DIR/architecture/architecture.md` | **一次入力**。とくに「8. データの配置」がこの設計の出発点。正本がどこかは**ここで決まっている**ので、勝手に変えない |
| `$DOCS_DIR/architecture/architecture-traceability.md` | コンポーネントと要件の対応。どのテーブルが誰に使われるかの裏取りに使う |
| `$DOCS_DIR/requirements/requirements.md` | ユースケースの基本フロー・入出力項目から、必要な属性を拾う |
| `$DOCS_DIR/requirements/requirements-traceability.md` | 要件 ID の全量と状態（確定/仮/要確認） |
| `$DOCS_DIR/database/` の既存ファイル | 差分更新のために必ず読む |

- `architecture.md` が無い場合は、**先に `dev-architecture-design` を実行するようユーザーに促す**。それでも進める場合は、データの配置を自分で仮定したことを設計書に明記する。
- **要件 ID（BR / UC / FR / NFR / CON / OUT / Q / R）とアーキテクチャ ID（CMP / IF / ADR / AR / AQ）は絶対に振り直さない。** 過不足があれば上流に戻して直す。
- 上流の状態が `仮` / `要確認` のものに依存するテーブル・列は、**その列も「仮」として扱う**。確定扱いにしない。

とくに次を重点的に読む:

1. **アーキテクチャの「データの配置」表** — どのデータの正本がオンチェーン／オフチェーン／外部サービスか。**これがこのスキルの設計範囲を決める。**
2. **アーキテクチャの「オンチェーンとオフチェーンの境界」** — なぜその線を引いたか。理由に反する設計をしない。
3. **個人情報・秘密情報の取り扱い** — 消せない場所に何を置くかに直結する。
4. **ユースケースの基本フロー** — 画面・API の入出力項目が、そのまま列になる。

## 2. 設計する

### 2-1. 設計範囲を確定する

アーキテクチャの「データの配置」を、次の 3 つに仕分ける。**この表を最初に作る。**

| 区分 | 扱い |
|---|---|
| オフチェーンが正本 | テーブルとして完全に設計する |
| オンチェーンが正本 | **オンチェーン側の構造を設計する**（2-5）。オフチェーンには投影テーブルを置き、「読み取り専用・不一致時はオンチェーンが正」と明記する |
| 外部サービスが正本 | テーブルには**参照用の識別子だけ**を持つ。本体を複製しない。複製する場合はキャッシュであることと有効期限を書く |

**アーキテクチャで「未定」となっているデータは、ここで勝手に決めない。** 仮置きしたうえで未決事項に上げる。

### 2-2. エンティティを洗い出す

ユースケースから拾う。思いつきで足さない。

1. **登場する対象物**（依頼・タスク・契約・成果物・評価 など）
2. **記録すべき出来事**（承認された・支払われた・申し立てられた など。履歴が要るものは独立したテーブルにする）
3. **アクター**（ただし正本が外部にある場合は 2-1 の仕分けに従う）

各エンティティについて「**このデータが無いと、どのユースケースのどの手順が成立しないか**」を言えること。言えないものは作らない。

### 2-3. 属性を決める

- ユースケースの入出力項目・画面項目・検索条件から導く。
- **型と長さの根拠を書く。** 「varchar(255)」を根拠なく置かない。
- 資料から決められない属性は、**仮置きして未決事項に上げる**。

### 2-4. リレーションを決める

- 1:1 / 1:N / N:M を判定し、**N:M は必ず中間テーブルに分解する**。
- 各リレーションについて、**必須か任意か**（NOT NULL か）を決める。
- 依存の向き（どちらが親か）を決める。循環参照を作らない。

### 2-5. オンチェーン側を設計する

**テーブルと同じ粒度で、オンチェーン側も設計する。** 「コントラクトに持つ」で済ませない。

次の 4 つを必ず出す:

1. **状態（state）** — struct / mapping / enum の定義。フィールド名・型・意味・不変か可変か。
   - 型は実際のものを使う（`uint256` / `address` / `bytes32` / `bool` / `enum`）。
   - **ストレージのコストを意識する**。文字列や配列を安易に持たない。長い値はハッシュか、オフチェーンの識別子にする。
2. **イベント（event）** — 名前・引数・`indexed` の指定。
   - **オフチェーンの投影テーブルは、このイベントだけを入力に構築できること。** できないなら、イベントの設計が足りない。
3. **値の型と精度** — 金額の単位（最小単位か、小数をどう扱うか）、時刻の型、識別子の生成規則。
   - 金額は浮動小数を使わない。オフチェーン側も対応する型にする（例: `numeric(78,0)`）。
4. **メタデータの構成** — 名前解決サービス（ENS 等）やトークンのメタデータに、**どのキーで何を入れるか**を定義する。
   - 名前の体系（どの階層に何を割り当てるか。例: `<用途>-<主体>.<親>.eth`、プロジェクトごとの subname）
   - レコードの種類（アドレスレコード / テキストレコード / contenthash）
   - **テキストレコードのキー設計** — キー名・値の形式・必須か任意か・誰が更新できるか を 1 件ずつ表にする。標準化済みのキー（`avatar`、`url`、`description` 等）があれば優先し、独自キーは名前空間を付ける。
   - 値に JSON を入れる場合は、**そのスキーマを定義する**（キー・型・必須・例）。
   - 更新権限（誰がそのレコードを書き換えられるか）を明記する。

### 2-6. 正本と同期を決める

オンチェーンが正本のデータをオフチェーンに投影する場合、次を必ず決める:

- 投影テーブルに **`tx_hash` / `block_number` / `chain_id` / `confirmed_at`** に相当する列を持たせるか（持たせないなら、どうやって確定を判別するか）
- **未確定の状態を表現できるか**（確定待ちと確定済みを区別できない設計にしない）
- イベントを取りこぼしたとき、チェーンが巻き戻ったときの**再同期の手順**
- 不整合が起きたときに**どちらを正とするか**（原則オンチェーン）

### 2-7. キー・インデックス・制約

- 主キー・外部キーを決める。外部キーには原則インデックスを張る。
- **ユースケースの検索条件から**インデックスを決める。思いつきで張らない。張った根拠（どのユースケースのどの検索か）を書く。
- 一意制約・CHECK 制約・NOT NULL を、**業務ルールの根拠とともに**書く。
  - 例: 「同じ案件に同じ人が二重にレビューできない」→ 一意制約。根拠となる要件 ID を添える。
- 列挙値（ステータス等）は**取りうる値をすべて列挙**し、遷移がある場合は遷移図か遷移表を書く。オンチェーンの enum と値がずれないようにする。

### 2-8. 個人情報・秘密情報

- 個人を特定できる情報を持つ列を洗い出し、**保持の可否と期間**を書く。上流が未定なら未決事項に上げる。
- **秘密鍵・パスワード・APIキーは DB に保存しない。**
- **消せない場所（オンチェーン）に個人情報を書かない。** 書く必要があるものは、ハッシュか匿名識別子にできないかを先に検討し、検討の結果を書く。

### 2-9. 命名規約

- テーブル名・カラム名は `snake_case`、テーブル名は**複数形**（例: `projects`）。
- 主キーは `id`（UUID か bigint。**どちらにしたか理由とともに設計書に書く**）。外部キーは `<単数形テーブル名>_id`。
- 全テーブルに `created_at` / `updated_at`（論理削除が要るなら `deleted_at`）を持たせる。
- 真偽値は `is_` / `has_` で始める。日時は `_at`、日付は `_on` で終える。
- 第3正規形を基本とし、**非正規化する場合は理由を書く**。
- ブロックチェーン系の型の目安:
  - アドレス: 小文字正規化した `varchar(42)`
  - トランザクションハッシュ / bytes32: `varchar(66)`
  - トークン量・wei: `numeric(78,0)`（浮動小数を使わない）
  - チェーン識別子: `integer`（`chain_id`）
- DBMS はアーキテクチャの技術選定に従う。**そこで「仮」とされているなら、この設計書でも「仮」と書く。**

### 2-10. ID の採番

| 対象 | ID | 備考 |
|---|---|---|
| テーブル | テーブル名そのもの | 別途 ID を振らない |
| オンチェーンの構造体・イベント | 名前そのもの | 同上 |
| データ設計上の未決事項 | `DQ-001` | 上流の `Q` / `AQ` とは別系列 |

- **上流（要件・アーキテクチャ）の欠落**を見つけた場合は `DQ` ではなく、**上流に `Q-nnn` / `AQ-nnn` を追加して差し戻す**（該当ファイルと、その変更履歴の両方を更新する）。`DQ` は「上流は決まっているが、データ設計の選択が残っている」ものに使う。
- 既存の設計書がある場合は必ず先に読み、**既存のテーブル名・ID を再利用して振り直さない**（廃止するものは行を残して「廃止」と記す）。

### 3-2. ER 図（SVG）

**ER 図は必ず SVG で作成し、`$DOCS_DIR/database/img/` に保存したうえで、その中身を `database-design.md` にインラインで埋め込む。** 画像リンクによる参照だけで済ませない — Markdown 単体で図が見える状態にする。

#### 描く要素

| 要素 | 記法 |
|---|---|
| エンティティ | 角丸の矩形。**上段にテーブル名**（太字）、区切り線、**下段に列を 1 行ずつ**。列は `列名 : 型` |
| 主キー | 列名の前に `PK`。下線を引いてもよい |
| 外部キー | 列名の前に `FK` |
| オンチェーンの構造 | 塗りを変え、上段のテーブル名の上に `«onchain»` を付ける（実体参照 `&#171;onchain&#187;` で書く） |
| 投影テーブル | 塗りを変え、`«projection»` を付ける。**正本ではないことが一目で分かるようにする** |
| 外部サービス参照 | `«external ref»` を付ける |
| 関連（1:N） | 実線。「1」側に短い直交線、「多」側に鳥の足（crow's foot） |
| 任意（0 を許す） | 端に小さな円（`○`）を足す |
| 識別関係 / 非識別関係 | 識別は実線、非識別は破線 |
| オンチェーン境界 | 破線の矩形で囲み、左上にラベル（例: `オンチェーン（Escrow コントラクト）`） |
| 凡例 | 図の下部に必ず置く |

- **オンチェーンとオフチェーンを 1 枚に描き、境界で分ける。** 両者をまたぐ参照（投影・識別子の対応）は線でつなぎ、ラベルに何で対応づくか（`tx_hash`、`project_id` など）を書く。
- 列が 12 を超えるエンティティは、**主キー・外部キー・業務上重要な列だけ**を図に出し、全列は設計書の表を正とする。その旨を図の注記に書く。

#### レイアウト規則

- **参照の向きを揃える**（親が上／左、子が下／右）。
- 関連の強いエンティティを近くに置き、**線を交差させない**。交差しそうならエンティティの並び順を入れ替える。
- エンティティが **15 を超えて読めなくなる場合は領域ごとに分割**し、`er-diagram-<領域名>.svg` として複数出力する。全体図も残す場合は `er-diagram.svg` を俯瞰図にする。
- 分割した場合は、**すべての図**を「4. ER 図」に順に埋め込み、各図の直前に `### <領域名>` と対象範囲を書く。

#### SVG の書き方（必須ルール）

- ルートは `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 W H" width="W" height="H">`。`viewBox` を必ず付ける。
- **ダーク/ライト両対応**: 背景に `<rect fill="#ffffff">` を敷き、線と文字は濃色（`#1f2937`）で描く。`currentColor` や CSS 変数に頼らない。
- フォントは `font-family="'Noto Sans JP','Hiragino Sans','Yu Gothic',sans-serif"`。テーブル名 `13`、列 `11`〜`12`。テキストは `<text>` 要素で書き、パス化しない。
- **列は 1 行 1 `<text>` で書く。** 等幅に見せるため、列名と型の x 座標を揃える（列名は左寄せ、型は別の x で左寄せ）。
- `<style>` 要素は使わず、すべて属性で指定する。
- 関連の端点記号（鳥の足・直交線・円）は `<defs>` の `<marker>` として定義して再利用する。**`id` は図ごとに一意にする**（同じ Markdown に複数の SVG を埋めると id が衝突するため）。
- `«` `»` などの記号は**必ず実体参照でエスケープする**（`&#171;` `&#187;`）。生で書くと XML として壊れる。
- 手書きで組み立てる。作図ツールの巨大な出力を貼り付けない。

#### 端点記号の骨組み

```svg
<defs>
  <!-- 「多」側：鳥の足 -->
  <marker id="crow-er" viewBox="0 0 12 12" refX="11" refY="6" markerWidth="12" markerHeight="12" orient="auto">
    <path d="M12,6 L0,0 M12,6 L0,6 M12,6 L0,12" fill="none" stroke="#64748b" stroke-width="1.4"/>
  </marker>
  <!-- 「1」側：直交する短い線 -->
  <marker id="one-er" viewBox="0 0 12 12" refX="6" refY="6" markerWidth="12" markerHeight="12" orient="auto">
    <path d="M6,1 L6,11" fill="none" stroke="#64748b" stroke-width="1.4"/>
  </marker>
  <!-- 任意（0 を許す）：小さな円 -->
  <marker id="zero-er" viewBox="0 0 12 12" refX="6" refY="6" markerWidth="12" markerHeight="12" orient="auto">
    <circle cx="6" cy="6" r="3.2" fill="#ffffff" stroke="#64748b" stroke-width="1.4"/>
  </marker>
</defs>
```

#### 埋め込み方

- 埋め込み位置は「4. ER 図」の中。
- `<svg>` 要素をそのまま本文に書く。前後を空行で挟み、**コードフェンスで囲まない**。
- 根要素の `xmlns="http://www.w3.org/2000/svg"` を必ず残し、**埋め込む側にだけ** `style="max-width:100%;height:auto"` を足す。
- 図の直後に `[図を SVG で開く](img/<ファイル名>.svg)` を 1 行添える（GitHub はインライン SVG を表示しないため）。
- 図の直前か直後に、**その図が何を示しているかを 1 行**書く。図だけ置かない。
- **インラインの中身は `.svg` ファイルから機械的にコピーする。** Markdown 側の SVG を手で編集しない。

## 4. 検証と報告

- [ ] アーキテクチャの「データの配置」に挙がっているデータが、**すべてこの設計書で扱われているか**（オフチェーン設計 / オンチェーン設計 / 参照のみ のいずれかに仕分けたか）

- [ ] すべてのテーブル・列・オンチェーンのフィールドに **根拠となる要件 ID** が付いているか（根拠が無い＝上流に無いものを足した。差し戻したか）
- [ ] すべてのユースケースが、いずれかのテーブルまたはオンチェーン構造に紐づいているか。紐づかないものは理由を書いたか
- [ ] **投影テーブルが、対応するイベントだけから構築できるか**（できないならイベント設計が足りない）
- [ ] 未確定の状態と確定済みの状態を区別できる設計になっているか
- [ ] N:M が中間テーブルに分解されているか。外部キーの参照先が実在するか。循環参照が無いか
- [ ] 一意制約・CHECK 制約に業務上の根拠（要件 ID）が付いているか
- [ ] インデックスに、どの検索のためかの根拠が書かれているか
- [ ] **秘密鍵・パスワードを DB に保存していないか。消せない場所（オンチェーン）に個人情報を書いていないか**
- [ ] 金額に浮動小数を使っていないか
- [ ] 列挙値がオフチェーンとオンチェーンでずれていないか
- [ ] DBMS・型などのうち上流で「仮」のものを、この設計書でも「仮」と書いたか（断定していないか）
- [ ] 要件 ID・アーキテクチャ ID を振り直していないか、`DQ` の ID が重複していないか
      （`grep -oE '\bDQ-[0-9]{3}\b' "$DOCS_DIR"/database/*.md | sort | uniq -c` で確認）
- [ ] 出力が Markdown（`.md`）で、見出しレベル・テーブル記法が崩れていないか
- [ ] 保存先が `$DOCS_DIR/database/` になっているか（リポジトリ内の `docs/` に書いていないか）
